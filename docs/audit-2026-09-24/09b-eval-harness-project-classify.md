### Findings

**F1.1 (S1) — Curated tier evaluates zero queries; `seed.json` is 100% placeholders.**
`evaluations/query_sets/seed.json` has 31 entries; every `expected_memory_id` starts with `00000000-` (30 numbered placeholders + one `_instructions` row). `eval_common.load_query_sets()` (`scripts/eval/eval_common.py:112-113`) skips anything starting with `00000000`, so `run_curated_eval` returns `{"total": 0}` (`eval_curated.py:43-45`). The file has not been touched since 2026-03-28 (git: only commit is the initial one). Every downstream tier that depends on curated entries (`cold_warm`, `ablation` — see below) is therefore also empty. The "curated benchmark" described in `docs/QUALITY-BASELINE-2026-06-06.md` (see §1b) does not exist as data.
Fix: populate at least 20-30 real ids (query against live DB), commit; or delete the file and the curated/cold_warm/ablation tiers so the harness stops advertising capability it lacks.

**F1.2 (S1) — No results have ever been persisted in this checkout.**
`evaluations/results/` is absent on disk (`ls evaluations` shows only `query_sets/`). `write_results()` (`eval_common.py:296-313`) would create it, so either the unified runner has never been executed from this repo root since 2026-03-28, or results were deleted. `eval_trends.py` ("reads past results") therefore has nothing to read. There is **no recorded last-result date, recall, or MRR** anywhere in the repo except the prose numbers in `docs/QUALITY-BASELINE-2026-06-06.md` (§1b). Fix: commit at least one results JSON (or a summary line in a tracked `evaluations/BASELINE.md`) so a regression has something to regress from.

**F1.3 (S2) — Golden tier works by reading, but the "golden set" is small and self-referential.**
`get_golden_queries()` (`src/dream_cycle_db.py:439-480`) reads `dream_cycle_candidates WHERE final_verdict='ACCEPTED' AND created_memory_id IS NOT NULL`, then regex-parses `content` for "Questions this answers:". Live DB (2026-09-24):
- 114 accepted candidates with a memory id; 110 have a "Questions this answers:" section; all 110 target memories still exist (104 active, 6 superseded); date range 2026-03-18 → 2026-09-23.
- Corpus size at the same moment: **124,280** memories.
So golden tier = ~110 insights × ~3-5 questions ≈ 300-550 queries, all generated by the dream cycle about dream-cycle-generated memories. It measures "can the LLM's own phrasing of its own insight find that insight" — a proxy for embedding self-consistency, not user-retrieval quality. Six targets are `superseded`, and `rerank()` applies `superseded_penalty` (-0.20 per `eval_common.py:47`), so those ~6×N queries are structurally penalised; the harness does not exclude them.
Fix: filter `m.status='active'` in `get_golden_queries` (or in `get_golden_queries_as_eval_entries`), and label the metric honestly as "insight self-retrieval".

**F1.4 (S2) — Imports resolve statically; runtime requires Bedrock.**
All eval modules import `src.embeddings.generate_embedding` → every tier except `trends` makes a model call per unique query. `eval_common.py:9-10` docstring claims scripts are "READ-ONLY against the database"; true (they call `hybrid_search`/`rerank` directly and bypass `increment_access_count`), verified by grep: no `increment_access_count` in `scripts/eval/`. But "no model calls" is false — the harness is not runnable in CI without Bedrock credentials. This is the reason no cheap regression gate exists.

**F1.5 (S2) — `run_evaluation.py` swallows tier failures and still writes a "full_eval" result.**
`run_evaluation.py:107-110` catches every exception, logs, stores `{"error": ...}`, and continues; `write_results("full_eval", ...)` at line 116 then persists a file with `corpus_size` and `git_commit` metadata that looks like a successful run. Exit code is always 0 (`main()` returns 0 at line 121). Fix: return non-zero if any tier errored.

**F1.6 (S3) — `get_eval_metadata()` runs `git rev-parse` from cwd, not repo root.**
`eval_common.py:283-288` executes `git rev-parse --short HEAD` without `cwd=`; correct only when invoked from repo root, which the `evaluations/results` relative path also assumes (`eval_common.py:302`). Fix: anchor both on `Path(__file__).resolve().parents[2]`.



**F1.7 (S2) — `cold_warm` and `ablation` re-score only the warm top-10, so they cannot measure recall changes.**
`eval_cold_warm.py:64-66` and `eval_ablation.py:66-70` call `rerank_with_overrides` on a *copy of the 10 results already returned by the production path* (`run_single_query` uses `limit=10`, `eval_common.py:145`). A candidate outside the production top-10 can never appear under the ablated weights, so `delta == "degraded"` where warm is None and cold found (`eval_cold_warm.py:75-76`) is unreachable, and every ablation "impact" is bounded by within-top-10 reordering. Fix: retrieve with `limit=50+` for the candidate pool, then compute rank@10 after re-scoring.

**F1.8 (S2) — `consolidation` tier reads `candidate_json.source_memories` but the eval can silently degrade if the field shape changes.**
`eval_consolidation.py:50` does `cj.get("source_memories", [])` with no type check. Live DB: 114/114 accepted candidates have a non-empty `source_memories` array (keys observed: `confidence, confidence_reasoning, content, operation, relationships, revision, schema_note, schema_operation, source_memories, strategy_that_found_it, supersedes_reason, target_memory_id, title, type`), so it works today. But `source_memories` contents are compared to `str(r["id"])` (`_find_rank` line 67-71) — if any candidate stores titles instead of UUIDs the insight trivially "outranks all sources" (empty `source_ranks` → `outranks` False; but `avg_rank_improvement` skips it). Low risk, noted as seam.

**F1.9 (S2) — The only enforced numeric gate is `recall_check.py --threshold 0.85`; it measures index recall, not relevance.**
`scripts/eval/recall_check.py:64-68`: `sys.exit(0 if mean >= threshold else 1)` over 10 hard-coded query strings, comparing HNSW top-10 to seqscan top-10. It requires an embedding call per query (10 Bedrock calls). It says nothing about whether the *right* memory is returned. It is wired only as a post-reindex hint (`scripts/jobs/reindex_embedding.sh:31` prints the command) — no scheduler runs it. `docs/VALIDATION.md:23` already states this limitation correctly.

**F1.10 (S3) — `tests/test_rerank_drift.py` is a scorer-agreement test, not a quality gate.**
Contrary to the audit brief's phrasing ("hand-set thresholds in tests/test_rerank_drift.py"), the file (`tests/test_rerank_drift.py:1-17`, tests at lines 187 and 248) asserts that `src.search.rerank` and `eval_common.rerank_with_overrides(PRODUCTION_WEIGHTS)` produce identical scores on seeded rows. There are no MRR/hit@k thresholds anywhere in `tests/` (grep for `mrr|hit_at|recall@` finds only `test_eval_properties.py:53-67`, which checks `0<=mrr<=1` and monotonic hit@k — property tests on `compute_metrics`, not on retrieval quality). **Conclusion: there is no retrieval-quality regression gate in the repo today.**

**F1.11 (S3) — `refactor_probe.py` is the de-facto regression check and is not repeatable.**
`scripts/eval/refactor_probe.py:10-16` records a five-point trajectory (baseline → HNSW rebuild: `distilled 10/12 | decision 4/4 | near_dup 0/12`) in a docstring — the only place any eval numbers are version-controlled. It has no expected ids (uses type/source_type proxies, lines 31,44-53), no threshold, always exits 0, and calls Bedrock 12×. Its "decision_recall_top3" is defined as *any* `source_type='distilled_chat'` row in top-3 (line 50), not the correct one.

### Findings

**F2.1 (S1) — Root cause of the UUID projects, verified: `cli_chat.parse_conversation` passes the JSONL session filename to the normaliser.**
`src/parsers/cli_chat.py:82-85` builds `conv_id = os.path.basename(path)[:-len(".jsonl")]` — a session UUID. `:178` calls `normalize_project_tag(conversation_id)`. `normalize_project_tag` (`src/project.py:6-60`) has no rule that rejects a UUID (rules: None/non-str, strip+lower, absolute-short-path guard, last path component, dot-prefix). A 36-char hex string passes every rule and is returned unchanged. `format_as_markdown(..., project=project)` writes `Project: <uuid>` into the header; `ingest.py:165-166` reads it back. This closes the "root cause not verified" gap left open in `04-express-briefing-feedback.md:107`. The unit tests (`tests/test_project.py:199-234`) exercise `parse_conversation` only with *path-shaped* ids (`/Users/kerrfir/AmplifyG2 Workshops/RetailStore`, `/Users/kerrfir`, `""`) that the current parser can never produce, so they are green while every live row is wrong. The property strategy `_conversation_id = st.from_regex(r"[a-zA-Z0-9_/\-]{1,50}")` (`tests/test_project_properties.py:287`) generates UUID-like strings but only asserts round-trip consistency, not "non-path → None" (Req 2.3).
Fix: (a) `parse_conversation` must not derive project from `conversation_id` at all — pass `None` (or a workspace/cwd if one exists in the JSONL `Prompt.meta`); (b) add `is_project_label()` guard (`^[0-9a-f]{8}-…$` → None) in `normalize_project_tag`; (c) a test that feeds a UUID id and asserts `project is None`; (d) one-off `UPDATE memories SET project=NULL WHERE project ~ '^[0-9a-f]{8}-'` (2,675 rows) — needs owner approval, not run here.

**F2.2 (S1) — `project_penalty` in `rerank()` is unreachable in production regardless of data.**
The only production caller that passes `query_project` is `mcp_server.memory_search` (`src/mcp_server.py:156-158`), and it passes the *same* value as `project=` to `hybrid_search`. `hybrid_search` filters `WHERE (project = %s OR project IS NULL)` (`src/search.py:62-63`). Therefore every result reaching `rerank` has `mem_project ∈ {query_project, NULL}`, and the penalty condition `query_project and mem_project and mem_project != query_project` (`src/search.py:295`) is **always False**. `_project_penalty` is 0.0 on every production result; the ablation condition `minus_project` (`eval_common.py:66`) and the `cold_warm` override are ablating a constant. The eval harness's `run_single_query` never passes `query_project` either (`eval_common.py:153-154`), so the eval can't see the penalty even in principle. 08b:273 and 09a call it a "noise floor"; it is exactly zero. The seeded drift test (`tests/test_rerank_drift.py:35-37, "decision_noclass_beta"`) reaches the branch only because it calls `rerank()` directly with a `query_project` and no `hybrid_search` filter — a code path no production caller uses.
Fix: decide one semantics — either *filter* (current SQL; delete the penalty branch, `PROJECT_PENALTY`, the `_project_penalty` plumbing, `minus_project` ablation, and the drift seed) or *soft-penalise* (drop the SQL filter, keep the penalty). Do not keep both.

**F2.3 (S2) — Cross-project detection in Express fires on session-UUID pairs; quantified.**
Live: of 114 accepted insights, 13 have `strategy_that_found_it = 'cross_project_collision'`; **5** have ≥2 distinct non-NULL source projects, and **all 5** of those project sets are UUID pairs. So `express.py:206-207` and `:626-628` (`len(projects) >= 2`) have never fired on a real project pair. (04 F3 already states the consequence; this adds the count and the writer.) `scripts/weekly_digest.py:198` filters `project !~ '^[0-9a-f-]{36}$'` — the UUID guard exists in one consumer and is missing from the writer, the normaliser, and Express.

**F2.4 (S2) — The one writer that has a *real* project name does not populate `memories.project`.**
`_explicit_codex_project` (`src/capture/sources/codex.py:293-336`) resolves a human label (live: "Getting back up to speed with Kiro" ×12, "AQD to Kiro migrations" ×6, …) but it is stored only under `metadata.codex_project.name` (`src/capture/codex.py:463-470`); `memories.project` is NULL for all 141 `codex_task` rows. Any future project-scoped search/penalty cannot see it. Note these names contain spaces and mixed case; `normalize_project_tag` would lowercase but not slugify them, so `"getting back up to speed with kiro"` would become a tag — decide slug rules before wiring it in.

**F2.5 (S3) — Substring / short-name containment risk: none in `project.py`, one latent in `backfill_projects.py`.**
Every live comparison is exact equality (`project = %s` in `search.py:63`; `mem_project != query_project` in `search.py:295`; set membership in `express.py:200-207`). `normalize_project_tag` never does `in`/`startswith` matching. Short names (`go`, `ai`, `qd`) are therefore safe from containment collisions *in retrieval*, though a 2-char tag is indistinguishable from noise and Rule 7 only guards absolute paths (`normalize_project_tag("go")` → `"go"`). The regex extractor in `scripts/backfill_projects.py:91` (`match.group(1)` on a `Project:` header) is the only pattern-based path and is dead (F-6.2). Recommend a minimum-length (≥3) and a denylist (`src`, `tmp`, `home`, `users`) if project tagging is kept.

**F2.6 (S3) — `normalize_project_tag` rule order comment vs code.** Docstring lists rules 1–7 "in order"; code applies 7 before 4 (comment at `project.py:34-35` explains why). Harmless, but `tests/test_project.py:1` says "exact examples from the design document" — the design's Rule 2.3 (non-path → None) has no example and no implementation. Seam: this function should own *all* rejection rules (dot-prefix, UUID/hex, short-path, min-length) so writers can't bypass them.

**Can project_penalty / cross-project logic ever work on this data?** No. (i) The penalty branch is dead by construction (F2.2). (ii) 99.85 % of non-NULL projects are session ids that never repeat across sources except when two chunks of the *same* session are cited (F2.3 — "cross-project" == "two CLI sessions"). (iii) 97.8 % of the corpus is NULL, which the SQL filter treats as "in every project". Until the writer is fixed and the column is nulled, any project-aware feature is measuring session identity, not project identity.



## 3. `src/classify.py` — memory classification

**Is `classify_memory` deterministic?** Yes. It is a pure function of `(type, content)`: one compiled regex (`PROCEDURAL_MARKERS`, `classify.py:19-24`) plus a set lookup (`SEMANTIC_TYPES`, `:10-13`). No randomness, time, DB, or I/O. Same input → same output, so it is safe to backfill and to re-run in tests. The `type == "source"` branch (`:43-44`) is redundant with the default (`:45`) — S3 dead branch.

Live `mem_class` (2026-09-24, 124,280 rows): `episodic` 44,127 · `procedural` 39,004 · **NULL 35,131** · `semantic` 5,877 · **`source` 141** (the brief's 117 has grown by 24 since the live-data track ran).

### Which writer skips classification (the 35,131 NULLs)
All NULLs are `type='source'` rows from three Quick Desktop sources: `quick_desktop_doc` 32,624 · `quick_desktop_feed` 1,803 · `quick_desktop_session_event` 704 (created 2026-05-17 → 2026-09-16). Writers: `scripts/migrate/ingest_doc_chunks.py:132-148` and `scripts/migrate/ingest_eventlog.py:127` call `create_memory(...)` **without `mem_class`** (and without `depth_score`); `db.create_memory` defaults `mem_class=None` (`src/db.py:89`). Neither script imports `src.classify`. (06 §2 identified the population; this pins the two call sites.)

### Which writer writes `'source'`
`src/capture/codex.py:546-553` (captured task, `'source'` literal in the VALUES list) and `:969-976` (topic segment, same literal). Both are raw SQL `INSERT INTO memories` that bypass `db.create_memory` and `classify_memory`. `'source'` is a *memory type*, not a memory class; the classifier vocabulary is `{semantic, episodic, procedural}` (`classify.py:36`). A third codex INSERT (`:997-1034`) correctly computes `episodic`/`semantic`.

### Findings

**F3.1 (S2) — Out-of-vocabulary `mem_class='source'` is silently scored 0.** `rerank()` does `MEM_CLASS_BOOST.get(mem_class, 0.0)`-style lookup (`search.py:~305`; `MEM_CLASS_BOOST = {"semantic": 0.04, "procedural": 0.02}` at `rerank_weights.py:34`), so `'source'` behaves like `episodic` — same as NULL. No CHECK constraint on `memories.mem_class` (schema above). Fix: `CHECK (mem_class IN ('semantic','episodic','procedural'))` after `UPDATE … SET mem_class = NULL WHERE mem_class='source'` (141 rows) or, better, route codex INSERTs through `create_memory` + `classify_memory`.

**F3.2 (S2) — The procedural rule is dominated by "any 3-line numbered list", and it overrides semantic types.**
Rule 1 fires before the type check (`classify.py:40-41`). Live decomposition of the 39,004 procedural rows: numbered-list pattern matches **34,373**, `how to` 10,560, `step-by-step` 2,482 (overlapping). By source: `kiro_ide_chat` 35,215 procedural vs 38,035 episodic — i.e. 48 % of IDE-chat chunks are "procedural" because assistant replies use `1. 2. 3.` lists. Consequence for ranking: procedural gets +0.02, so half the IDE-chat corpus carries a boost that a genuine `decision`/`insight` without a list does not, and **72 `insight`, 4 `synthesis`, 1 `connection` rows are demoted from semantic (+0.04) to procedural (+0.02)** purely because their content contains a numbered list. Fix: check `type in SEMANTIC_TYPES` *first* (type is authoritative for dream-cycle/MCP writers); apply the procedural regex only to `type='source'`; require ≥2 markers or a "how to"/imperative title for `procedural`.

**F3.3 (S3) — `SEMANTIC_TYPES` omits `research` and `correction_episode`.** Live `research` rows are 138 semantic / 1 episodic only because `quick_desktop_terminology`'s migrator hard-codes `mem_class="semantic"` (also `distill_sessions.py:190`, `redistill_capped.py:178`, `weekly_digest.py:255` hard-code it). Through `classify_memory("research", …)` they would be episodic. `correction_episode` (16 rows) is classified by codex directly as episodic (`codex.py:997-1001`), bypassing the function. Two vocabularies for the same decision. Fix: `classify_memory` becomes the only writer of `mem_class`; hard-coded literals removed.

**F3.4 (S3) — Test coverage is a single property test.** `tests/test_classify.py` has one test (`:53 test_classifier_correctness`) that re-implements the rules; there is no example test for the numbered-list false-positive on semantic types, and none asserting `'source'` is never emitted. `MEM_CLASS_BOOST` has no `'source'` key and nothing tests that every live class is in the boost dict or intentionally absent.

## 4. `src/depth.py` — depth score

**What it does.** `compute_depth_score(content)` (`depth.py:139-191`) is a pure, deterministic regex bag: causal connectors (≤0.35), fenced code blocks (≤0.20), a "Questions this answers:" header (+0.25), word count ramp (≤0.10), specific numbers (≤0.08), a fixed list of ~40 tool names (≤0.08), connection phrases (≤0.08); clamped to [0,1]; only the first 10,000 chars are scanned (`:157`). Note `_CAUSAL_RE` includes `→` and `\bthe\s+fix\b` (`:20-33`) — chat transcripts about code hit these constantly. `extract_questions()` (`:71-134`) duplicates `dream_cycle_db.extract_golden_queries` (`dream_cycle_db.py:483-517`) with slightly different whitespace rules (S3 duplicate).

**Who writes it.** `metadata.depth_score` via `ingest.py:173-174` (parent), `dream_cycle/storage.py:23,63`, `capture_api.py:106-109`, `mcp_server.py:97-100,288`. The two QD migrate scripts and codex do not write it.

**Who reads it.**
- `rerank()` — `search.py:287` reads `metadata.depth_score` (default 0.0) and adds `COEFFICIENTS["depth"] * depth` = **0.05 × depth** (`rerank_weights.py:25`). Max contribution 0.05 of a ~1.1 sum.
- `mcp_server.memory_create:109` — warns the caller if `depth_score < 0.3`.
- Express `_gather_resurfaced` (`express.py:282,296`) — as a tiebreaker after `access_count DESC`.
- Explorer prompt (`prompts/explorer.py:48,157`) — "DESIRABLE DIFFICULTY SURFACING — find memories with high depth_score (>= 0.7)".
- Eval: `eval_depth_experiment.py`, `minus_depth` ablation.

**Live distribution.** 83,135 rows have `depth_score`; 75,355 of those are searchable (have an embedding). By source: `kiro_ide_chat` 73,250 rows, mean 0.52, median 0.52, **5,996 ≥ 0.7**; `kiro_cli_chat` mean 0.56, 777 ≥ 0.7; dream-cycle memories (`source_type` NULL, 88 rows) mean 0.62, 39 ≥ 0.7; `article` mean 0.34, 0 ≥ 0.7; `outlook_calendar` mean 0.13.

### Findings

**F4.1 (S1) — Every chunk inherits its *parent's* depth score; the reranker never sees the chunk's own depth.**
`ingest.py:173-174` computes `depth_score` once over the whole `body` (first 10k chars) and puts it in `meta`; `:202` gives each chunk `metadata={**meta, "chunk_index": …}`. Parents have no embedding (`ingest.py:176-177`) so only chunks are retrievable. Live: **74,633 of 75,257 chunks (99.2 %) have a `depth_score` byte-identical to their parent's.** The 0.05·depth term therefore rewards "came from a long chat with lists and arrows", uniformly across all chunks of that chat, and cannot distinguish the explanatory chunk from the filler chunk beside it. The design premise (Craik & Lockhart depth-of-processing at the *memory* level) is not what is computed. Fix: `compute_depth_score(chunk_text)` per chunk in `ingest.py:192-206` (cheap, pure), and backfill.

## 5. `access_count` / `last_accessed_at` — access reinforcement

**Exactly one code path increments.** `grep increment_access_count` → definition `src/search.py:337-345` (`UPDATE … access_count = coalesce(access_count,0)+1, last_accessed_at = now()`), and a single caller `src/mcp_server.py:160` inside `memory_search`, applied to *every* returned row (all `limit` results, not the one the agent reads). No other writer: `memory_read`, `memory_graph`, Express, weekly digest, `distill_sessions.py:108` (calls `rerank` directly), and all `scripts/eval/*` bypass it. `memory_brief`/`memory_learn` (`mcp_server.py:449-451`) call `hybrid_search`+`rerank` directly → no increment.

**Who calls `memory_search`.** (a) the user's agents (Kiro CLI/IDE); (b) the dream-cycle Explorer, which runs *as* an MCP client (`backends/kiro.py:80`, `dream_cycle/packet.py:40` — "memory_search to find existing …"); (c) **`MCPStartupProbe`** (`backends/mcp_probe.py:170-178`): every agentic stage begins with `memory_search("__mcp_startup_probe__", limit=1)`. The probe's docstring calls the tool "read-only" (`:172`); it is not — `hybrid_search` always returns a nearest neighbour for a nonsense query, so one arbitrary memory gets `access_count += 1` on every stage start of every run. Live: 2,142 rows accessed, 4,712 total hits, 22 distinct access days (= dream-cycle run dates, per 06 §7), max 70 on a `kiro_cli_chat` parent; the top-8 are 4 CLI chat parents and 4 dream-cycle insights.

**Is the reinforcement term self-referential?** Yes, structurally, and in two ways beyond what 06 §7 reported:
1. The term `0.03·log1p(access)·spacing_bonus` (`search.py:~311`; `REINFORCEMENT_COEFF` at `rerank_weights.py:29`) *and* the recency stability `S = 30 + 10·log1p(access)` (`search.py:262-265`) both grow with the same counter. So a dream-cycle hit both boosts and slows the decay of whatever the previous dream cycle retrieved — two coupled feedback paths from one machine-generated signal.
2. `increment_access_count` is applied to all `limit` results (default 10), not to what the agent actually used. An Explorer that runs 20 searches at limit 10 "reinforces" 200 memories per run. Reinforcement therefore encodes "was in a top-10 for some Explorer query", which is exactly what the reranker already computed — the term feeds the ranker its own prior output.
Also: 618 rows have `last_accessed_at` set with `access_count = 0` (backfill artefact; 06 §7), which gives them `spacing_bonus` computed from a date but zero reinforcement — harmless but inconsistent.

**F5.1 (S1)** — Reinforcement and recency-stability are fed ~75 % by dream-cycle and probe traffic; there is no `accessed_by` attribution, so the user share cannot be separated. Fix (minimal): pass a `source` flag from the MCP tool (`memory_search(…, _caller="dream_cycle")` is not possible from the client side, but the probe query string is a fixed constant — at minimum `if query == MCPStartupProbe.QUERY: skip increment`), or add an `accessed_by` column and count only user-agent sessions in `rerank`. Until then set `REINFORCEMENT_COEFF = 0` and drop `access` from the stability formula; the eval `minus_reinforcement` condition (`eval_common.py:68`) exists for exactly this comparison but has never been persisted.

**F5.2 (S3)** — `eval_common.py:5-8` docstring is correct that eval bypasses the increment; `mcp_probe.py:172` docstring ("read-only tool") is wrong. Same fact, opposite claims in two files.

## 6. Recommended minimal retrieval regression check (no model calls)

Constraint: the refactor needs a gate that runs in seconds, needs no Bedrock, and fails deterministically when ranking behaviour changes. Everything in `scripts/eval/*` fails at least one of those. The design below reuses what already exists.

### 6.1 Principle
Freeze the *inputs* to the ranking stage, not the model. `hybrid_search` needs a query embedding; `rerank` needs only rows + query text. Both are pure given a DB snapshot. So: store query embeddings once, store expected ids once, compare ranks.

### 6.2 Fixture (committed, ~200 KB)
`tests/fixtures/retrieval_regression/`
- `queries.json` — 30–50 entries `{id, query, embedding: [1024 floats], expected_ids: [uuid, …], k: 5}`. Sources for queries/expected ids, in order of independence:
  1. the 10 `recall_check.QUERIES` + 12 `refactor_probe.QUERIES` (already chosen by the owner; run their embeddings **once**, offline, and pin them);
  2. 20 golden queries whose target is `status='active'` (pick from `get_golden_queries()`; pin `memory_id` as expected);
  3. fill `evaluations/query_sets/seed.json` categories with real ids (closes F1.1) — the same file can carry the pinned embedding.
- `expected_ranks.json` — generated once by running the pipeline at the baseline commit: per query, the ordered top-10 ids and `rerank_score`s.

Embedding pinning is legitimate because the embedding model is not what the refactor changes; if it ever does, regenerate the fixture in one deliberate commit.

### 6.3 Test (`tests/test_retrieval_quality_gate.py`, DB-backed, marked `@pytest.mark.db`)
```
for q in fixture:
    rows = hybrid_search(q.query, q.embedding, limit=50)      # no model call
    ranked = rerank(rows, q.query)                            # pure
    top = [str(r["id"]) for r in ranked[:10]]
    assert expected_ids ⊆ set(top[:q.k])                      # hit@k must not regress
    assert kendall_tau(top, baseline_top) >= 0.8              # ordering stable within tolerance
    assert abs(mrr(all) - baseline_mrr) <= 0.02               # aggregate gate
```
Also assert the invariants that are currently only in docstrings: `_project_penalty == 0` for all rows when `query_project` is None (F2.2), every `mem_class` in results ∈ {semantic, episodic, procedural, None} (F3.1), `_depth_score ∈ [0,1]`.

### 6.4 Why this is enough for the refactor
- Any change to `hybrid_search` SQL, RRF constant, prefetch, dedup, or to any `rerank` term changes `top`/`rerank_score` and is caught with pinpoint diffs.
- Runs against the live DB in < 10 s (50 queries × 1 vector + 1 FTS query). No writes (does not call `increment_access_count`).
- Corpus drift: the DB grows ~30 rows/day; the tolerance (`hit@k` on pinned ids, τ ≥ 0.8, ΔMRR ≤ 0.02) absorbs that. If the fixture ever needs re-baselining, that is a *visible* commit, unlike today's unrecorded drift.
- Cost: zero Bedrock calls after the one-off fixture generation (≈50 embedding calls).

### 6.5 What it deliberately does not do
It does not measure *usefulness* (whether the expected id is the right answer) — that is what the golden/consolidation tiers and human review are for, and they can stay expensive and manual. It measures *behavioural stability of the ranking function* — the property a refactor must preserve.

### 6.6 Housekeeping the gate exposes
- Delete or fix `seed.json` placeholders (F1.1); make `run_evaluation.py` exit non-zero on tier error (F1.5); write `corpus_size`+`git_commit` into any doc that quotes metrics (F1.12).
- Remove the dead `project_penalty` path or the SQL filter (F2.2) *before* baselining, so the fixture does not freeze a no-op.
- Decide F4.1 (per-chunk depth) before baselining; it changes `_depth_score` on 75k rows.
