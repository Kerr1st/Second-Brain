## 1. What this pass changes about the picture

The first audit's shape was right — nine features' worth of correct code that never had a second pass, with the defects clustering into "rule stated but not enforced", "failure caught then reported as success", "same thing N times, drifted", "identity by substring", and "docs asserting present-tense authority from a stale commit". This pass confirms that shape and corrects the specifics in four places that change what to do first.

**The routing rule is being violated tonight, not hypothetically.** Your rule is that corpus content never reaches Kiro or Fable 5.1. The first audit found two paths that *could*. There are five, and two of them run every night under the `controlled` profile that was supposed to make scheduled runs safe:

- `scripts/distill_sessions.py:27,150` constructs `KiroInvoker(...)` directly, bypassing the resolver, and sends full chat transcripts (≤100 k chars, ≤40 sessions) at 05:00 daily. kiro-cli ≥ 2.22 ignores `--model`, so the server chooses; the model's own refusal text — "not approved for customer data / PII" — appears in 76 log lines across seven nights, one flagged session was re-sent thirteen times, and 195 memories were written by whatever model Auto chose. Since 09-23 the job also fails 100 % and reports OK. (F-003, F-008)
- `scripts/jobs/dream_cycle_scheduled.sh:44` chains `express_push.py` after every scheduled run; `express.py:481` builds `AgentInvoker()` = Kiro. It fired 09-18 ×2, 09-21, 09-23 — and every result was discarded, because `email_configured()` is checked *after* the LLM pass and no email has ever been configured. (F-001)
- `redistill_capped.py:126`, `memory_brief(use_llm=True)` (client-triggerable from any MCP session), and the Codex semantic pass (Opus 5, ~$0.44 per call, unmetered, O(n²) re-send) are the other three. (F-002, F-005)

**The "199 MB never embedded" headline was ~10× too large.** Of 4,833 rows over 25 k chars, 4,166 are *parents*, which carry no embedding by design because their text is duplicated into chunks. The real tail loss is 19.8 MB in 667 embedded rows. The chunker defect stands — 14,338 chunks (19 %) exceed the declared 4 k limit — but the storage problem is duplication, and it is large: **62,384 of 67,757 `kiro_ide_chat` chunks are byte-identical to another chunk** (261 MB of individually embedded duplicate text), 1,491 duplicate parents exist under different URLs (76 MB), and 52 % of all corpus text is an exact duplicate of other corpus text. This has a direct retrieval consequence: `hybrid_search` dedups after a fixed prefetch, so a chat-heavy neighbourhood returns 1 distinct row for `limit=10`. (F-020, F-022, F-023, F-047)

**"97 % of relationships expired" has a root cause, and the first plan's fix would have made it worse.** `expire_stale_relationships` (`dream_cycle_db.py:835`, run every cycle) treats `last_accessed_at IS NULL` as stale with no grace period. Nothing but a search hit ever sets `last_accessed_at`, so edges between never-searched memories die on the next run: 18,044 of 22,461 expirations happened within one day of creation; every September `contradicts` edge — the trigger Express relies on — was expired within hours; 88 Codex `derived_from` provenance edges were expired, which origin/main's migration 012 forbids by CHECK constraint and which was never ported. Filtering expired edges out of `memory_graph` first, as the first plan proposed, would leave 922 live edges of 23,383. (F-025, F-046)

**The largest capture channel is dead.** `kiro_ide_chat` is 59 % of the corpus (73,250 rows) and every row was written between 12:19 and 12:49 on 2026-05-17. All 31 nightly logs since end `IDE=0`. Kiro moved its session store to `~/.kiro/sessions/<hash>/` (1,027 files since 09-20) and no parser reads it. The liveness monitor never noticed because it has no "channel that used to produce output now produces zero" predicate. (F-083)
