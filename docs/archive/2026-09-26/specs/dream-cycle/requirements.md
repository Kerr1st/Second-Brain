# Requirements Document

> **Note**: This spec has been partially superseded by the Byzantine Consensus Panel
> spec (`.kiro/specs/byzantine-consensus-panel/`). Key changes: the consensus panel
> was upgraded from 3 to 4 evaluators with binary BFT consensus (≥3/4 ACCEPTED,
> ≤2/4 REJECTED). The DEFERRED state, two-strike rule, and Explorer Strategy #11
> (deferred evidence gathering) were removed. Requirements 2, 3, 10, and 11 below
> reflect the original design; see the BFT spec for the current implementation.

## Introduction

The Dream Cycle adds autonomous, proactive learning to the Second Brain personal knowledge management system. A four-agent pipeline (Explorer → Thinker → Consensus Panel of 3 evaluators) runs during downtime to examine the 74K+ memory space, discover hidden connections, surface contradictions, name implicit principles, and store consensus-gated insights as new semantic memories. This implements Speed 3 of the Three-Speed Enrichment architecture and replaces V2 Task 8 (Consolidation Pipeline) with a research-grounded multi-agent approach.

## Glossary

- **Orchestrator**: The central coordination module (`src/dream_cycle.py`) that manages the four-agent pipeline lifecycle, consensus tallying, deduplication, memory storage, and digest generation.
- **Explorer**: Agent 1 in the pipeline. Autonomously decides what regions of the memory space to examine and assembles curated "memory slices" of 10-20 memories.
- **Thinker**: Agent 2 in the pipeline. Receives memory slices and generates candidate insights by finding patterns, contradictions, and implicit principles.
- **Consensus_Panel**: Agents 3a/3b/3c — three independent evaluators (Skeptic, User Advocate, Epistemologist) that assess each candidate insight. Unanimous 3/3 agreement required for acceptance.
- **Memory_Slice**: A curated set of 10-20 memories assembled by the Explorer using a named strategy, accompanied by a hypothesis for the Thinker.
- **Candidate_Insight**: A fully-formed insight generated by the Thinker, including title, content, operation type, confidence, source memories, and proposed relationships.
- **Evaluator_Verdict**: A binary ACCEPT or REJECT decision from a single evaluator, with reasoning text.
- **Feedback_Injection**: A text block containing rejection/deferral reasons from the last 3 dream cycles, injected into the Explorer's prompt to drive improvement.
- **Deferred_Insight**: A candidate that received 2/3 consensus — re-enters the next cycle with the dissenting objection as context.
- **Two_Strike_Rule**: A deferred insight that fails consensus a second consecutive time is marked REJECTED with `deferred_twice_rejected = TRUE`.
- **Deduplication_Check**: Embedding similarity comparison (threshold > 0.85) against existing active non-chunk memories before storing an accepted insight.
- **Circuit_Breaker**: Early abort mechanism — if the Explorer returns 0 slices, the Thinker and Panel are skipped entirely.
- **Digest**: A static markdown file summarizing the dream cycle's results, grouped by strategy type.
- **Dream_Cycle_DB**: The database layer (`src/dream_cycle_db.py`) for dream-cycle-specific operations on `dream_cycle_runs` and `dream_cycle_candidates` tables.
- **Agent_Invoker**: The abstraction layer (`src/agent_invoker.py`) for spawning `kiro --no-interactive` subprocesses with system prompts and input payloads.
- **SUPERSEDE_Operation**: A Thinker-proposed operation that creates a new memory and marks the old memory as superseded, with a `superseded_by` relationship.
- **Briefing_Frequency_Cap**: Session-start runs are limited to at most once per 24 hours AND require either new memories or a completed dream cycle since the last session.

## Requirements

### Requirement 1: Pipeline Orchestration

**User Story:** As a knowledge system owner, I want the dream cycle to execute a four-agent pipeline in the correct order, so that insights are explored, generated, and quality-gated before storage.

#### Acceptance Criteria

1. WHEN a dream cycle run is triggered, THE Orchestrator SHALL create a `dream_cycle_runs` record with the run_type and started_at timestamp before invoking any agents.
2. WHEN the Explorer completes, THE Orchestrator SHALL pass each memory slice to the Thinker sequentially, collecting candidate insights.
3. WHEN the Thinker completes for all slices, THE Orchestrator SHALL send each candidate insight to all three evaluators independently.
4. WHEN all evaluators return verdicts for a candidate, THE Orchestrator SHALL tally consensus: 3/3 ACCEPT = ACCEPTED, 2/3 ACCEPT = DEFERRED, otherwise REJECTED.
5. WHEN the pipeline completes, THE Orchestrator SHALL update the `dream_cycle_runs` record with completed_at, candidate counts, and digest text.
6. THE Orchestrator SHALL store every candidate with its verdicts in `dream_cycle_candidates` regardless of the final verdict.

### Requirement 2: Consensus Protocol

**User Story:** As a knowledge system owner, I want unanimous 3/3 consensus to be required permanently, so that only high-quality insights enter the memory space.

#### Acceptance Criteria

1. WHEN a candidate receives 3 ACCEPT verdicts, THE Orchestrator SHALL mark the candidate as ACCEPTED and proceed to deduplication and storage.
2. WHEN a candidate receives exactly 2 ACCEPT verdicts, THE Orchestrator SHALL mark the candidate as DEFERRED and preserve the dissenting evaluator's reasoning.
3. WHEN a candidate receives fewer than 2 ACCEPT verdicts, THE Orchestrator SHALL mark the candidate as REJECTED.
4. THE Consensus_Panel SHALL evaluate each candidate independently — no evaluator's prompt contains another evaluator's verdict or reasoning.
5. THE Orchestrator SHALL record each evaluator's individual verdict and full reasoning text in the `dream_cycle_candidates` record.

### Requirement 3: Explorer Agent

**User Story:** As a knowledge system owner, I want the Explorer to use diverse strategies to examine the memory space, so that non-obvious connections and patterns are discovered.

#### Acceptance Criteria

1. THE Explorer SHALL support 11 named exploration strategies: temporal juxtaposition, cross-project collision, orphan archaeology, question-answer bridging, contradiction hunting, pattern emergence, depth gradient, stale synthesis check, retrieval failure analysis, desirable difficulty surfacing, and deferred evidence gathering.
2. WHEN executing a scheduled run, THE Explorer SHALL use at least 3 different strategies per cycle and vary strategy selection across cycles.
3. WHEN executing a session_start run, THE Explorer SHALL use only strategies 6 (pattern emergence), 8 (stale synthesis check), and 10 (desirable difficulty surfacing).
4. WHEN executing a post_learn run, THE Explorer SHALL scope exploration to the new insights and their semantic neighbors.
5. THE Explorer SHALL return 0-5 Memory_Slice objects, each containing 10-20 memory IDs that exist in the database.
6. WHEN no strategies yield interesting slices, THE Explorer SHALL return an empty list rather than forcing weak slices.

### Requirement 4: Feedback Injection

**User Story:** As a knowledge system owner, I want the Explorer to learn from previous cycles' rejections, so that insight quality improves over time.

#### Acceptance Criteria

1. WHEN a dream cycle starts, THE Orchestrator SHALL query the last 3 cycles' rejected and deferred candidates with their evaluator reasoning.
2. THE Orchestrator SHALL format the rejection data as a "Lessons from recent cycles" text block containing the actual evaluator reasoning, not just statistical counts.
3. THE Orchestrator SHALL inject the feedback text into the Explorer's prompt before invocation.
4. WHEN no previous cycles exist, THE Orchestrator SHALL pass an empty feedback string to the Explorer.

### Requirement 5: Thinker Agent

**User Story:** As a knowledge system owner, I want the Thinker to generate high-quality candidate insights from memory slices, so that the system discovers connections, patterns, and contradictions.

#### Acceptance Criteria

1. WHEN the Thinker receives a memory slice, THE Thinker SHALL generate 0-3 Candidate_Insight objects per slice.
2. THE Thinker SHALL support 9 insight categories: unnamed principles, contradictions, resolved questions, emerging patterns, knowledge gaps, stale knowledge, meta-cognitive reflection, CLS interleaving, and distillation.
3. THE Thinker SHALL support 3 operations: CREATE (new memory), UPDATE (modify existing), and SUPERSEDE (replace existing with new).
4. WHEN generating a candidate, THE Thinker SHALL include the depth framework: WHAT (the insight), EVIDENCE (source memory IDs and quotes), and WHY IT MATTERS (actionable implication).
5. WHEN generating a candidate, THE Thinker SHALL include a "Questions this answers" section with 3-5 natural-language queries.
6. WHEN generating a candidate, THE Thinker SHALL classify the schema operation as either assimilation (reinforcing existing schema) or accommodation (changing existing schema).
7. WHEN deferred candidates from the previous cycle are provided, THE Thinker SHALL re-evaluate them with the dissenting objection as additional context.

### Requirement 6: Evaluator Agents

**User Story:** As a knowledge system owner, I want three specialized evaluators to independently assess each candidate, so that insights are vetted from diverse perspectives.

#### Acceptance Criteria

1. THE Skeptic evaluator SHALL assess candidates on factual grounding, non-obviousness, logical validity, and actionability.
2. THE User_Advocate evaluator SHALL assess candidates on relevance to current work, timing, signal-to-noise ratio, and depth of explanation.
3. THE Epistemologist evaluator SHALL assess candidates on evidence sufficiency, falsifiability, novelty, durability, and retrievability. WHEN assessing novelty, THE Epistemologist SHALL weight accommodation insights (schema_operation = 'accommodation') as inherently higher novelty than assimilation insights (schema_operation = 'assimilation'), because accommodation represents genuine schema change while assimilation is schema confirmation.
4. WHEN evaluating UPDATE or SUPERSEDE operations, THE Skeptic SHALL apply additional scrutiny on preservation of existing knowledge and evidence delta.
5. THE Consensus_Panel SHALL return exactly one verdict per evaluator per candidate: ACCEPT or REJECT with non-empty reasoning.

### Requirement 7: Deduplication

**User Story:** As a knowledge system owner, I want accepted insights to be checked for duplicates before storage, so that the memory space does not accumulate redundant knowledge.

#### Acceptance Criteria

1. WHEN a candidate is ACCEPTED, THE Orchestrator SHALL generate an embedding for the candidate content and compare it against existing active non-chunk memories.
2. WHEN embedding similarity exceeds 0.85 for any existing memory, THE Orchestrator SHALL skip creation and log the candidate as "already known" with the matched memory ID.
3. WHEN no existing memory exceeds the 0.85 similarity threshold, THE Orchestrator SHALL proceed with memory creation.
4. THE Deduplication_Check SHALL only compare against memories where parent_id IS NULL and status = 'active'.

### Requirement 8: Memory Storage Operations

**User Story:** As a knowledge system owner, I want accepted insights to be stored correctly based on their operation type, so that the knowledge graph evolves accurately.

#### Acceptance Criteria

1. WHEN a CREATE operation is accepted, THE Orchestrator SHALL create a new memory with embedding, tags including 'dream-cycle' and the schema_operation, and metadata containing the strategy, source memories, and confidence.
2. WHEN an UPDATE operation is accepted, THE Orchestrator SHALL update the target memory's content and re-embed it.
3. WHEN a SUPERSEDE operation is accepted, THE Orchestrator SHALL create a new memory, set the old memory's status to 'superseded', and create a 'superseded_by' relationship from old to new.
4. WHEN a SUPERSEDE operation is accepted, THE Orchestrator SHALL preserve all existing relationships on the old memory.
5. THE Orchestrator SHALL create all proposed relationships for each accepted insight.
6. IF a SUPERSEDE target memory does not exist or is already superseded, THEN THE Orchestrator SHALL downgrade the operation to CREATE and log a warning.

### Requirement 9: Circuit Breaker

**User Story:** As a knowledge system owner, I want the pipeline to abort early when the Explorer finds nothing interesting, so that Kiro credits are not wasted on empty cycles.

#### Acceptance Criteria

1. WHEN the Explorer returns 0 memory slices, THE Orchestrator SHALL skip all Thinker and Panel invocations.
2. WHEN the circuit breaker fires, THE Orchestrator SHALL complete the run with candidates_generated = 0 and aborted_early = TRUE.
3. WHEN the circuit breaker fires, THE Orchestrator SHALL update the `dream_cycle_runs` record with completion time and zero candidate counts.

### Requirement 10: Deferred Insight Re-evaluation

**User Story:** As a knowledge system owner, I want deferred insights to get a second chance with additional evidence, so that near-miss insights are not permanently lost.

#### Acceptance Criteria

1. WHEN a candidate is DEFERRED, THE Orchestrator SHALL preserve the dissenting evaluator's objection in the `dream_cycle_candidates` record.
2. WHEN the next cycle runs, THE Explorer SHALL use strategy 11 (deferred evidence gathering) to assemble new slices addressing the dissenting objection.
3. WHEN the Thinker receives deferred candidates, THE Thinker SHALL re-evaluate them with both the original candidate and the dissenting objection as context.
4. WHEN a deferred candidate fails consensus a second consecutive time, THE Orchestrator SHALL mark it as REJECTED with `deferred_twice_rejected = TRUE`.
5. THE Orchestrator SHALL NOT maintain a permanent blocklist — independently rediscovered insights in future cycles are evaluated fresh.

### Requirement 11: Execution Modes

**User Story:** As a knowledge system owner, I want four execution modes with appropriate scoping, so that the dream cycle runs at the right time with the right scope.

#### Acceptance Criteria

1. THE Orchestrator SHALL support 4 execution modes: scheduled, post_learn, session_start, and user_triggered.
2. WHEN run_type is 'scheduled', THE Orchestrator SHALL execute the full pipeline with all 11 Explorer strategies.
3. WHEN run_type is 'post_learn', THE Orchestrator SHALL scope the Explorer to new insights from the session and their neighbors. For v1, post-learn reflection is triggered manually via `scripts/dream_cycle_run.py --run-type post_learn --memory-ids uuid1,uuid2,...` after a learning session. Automatic session-end detection is a v2 enhancement.
4. WHEN run_type is 'session_start', THE Orchestrator SHALL limit the Explorer to strategies 6, 8, and 10, and limit the Thinker to 1-2 candidates.
5. WHILE run_type is 'session_start', THE Orchestrator SHALL enforce a 24-hour minimum gap since the last session_start run.
6. WHILE run_type is 'session_start', THE Orchestrator SHALL require that either new memories exist or a dream cycle ran since the last session.
7. WHEN run_type is 'user_triggered', THE Orchestrator SHALL scope the Explorer to the user-specified topic using all strategies.

### Requirement 12: Digest Generation

**User Story:** As a knowledge system owner, I want a readable digest of each dream cycle's results, so that I can review and act on the insights discovered.

#### Acceptance Criteria

1. WHEN a dream cycle completes with accepted insights, THE Orchestrator SHALL generate a static markdown digest file at `logs/dream-cycle-digest-{date}.md`.
2. THE Digest SHALL group accepted insights by strategy type, not by confidence level.
3. THE Digest SHALL include for each accepted insight: a 1-line summary, full content, source memory links, and evaluator reasoning.
4. WHEN an accepted insight uses UPDATE or SUPERSEDE, THE Digest SHALL show a diff with a link to the original memory.
5. THE Digest SHALL include run statistics: candidates generated, accepted, deferred, and rejected.
6. THE Digest SHALL include the Explorer strategies used and the feedback loop summary.

### Requirement 13: Agent Invocation

**User Story:** As a knowledge system owner, I want each agent to run as an isolated subprocess, so that agents have independent context windows and failure isolation.

#### Acceptance Criteria

1. THE Agent_Invoker SHALL invoke each agent as a separate `kiro --no-interactive` subprocess with a dedicated system prompt.
2. THE Agent_Invoker SHALL enforce a configurable timeout per agent invocation, defaulting to 300 seconds.
3. WHEN an agent subprocess returns output, THE Agent_Invoker SHALL parse JSON from the output, handling markdown code fence wrapping.
4. THE Agent_Invoker SHALL provide MCP server configuration to the Explorer and Thinker agents, and no MCP configuration to evaluator agents.
5. IF an agent subprocess crashes or times out, THEN THE Agent_Invoker SHALL raise an exception with the full stderr output for the Orchestrator to handle.

### Requirement 14: Database Schema

**User Story:** As a knowledge system owner, I want dedicated database tables for dream cycle tracking, so that run history, candidate verdicts, and metrics are persisted.

#### Acceptance Criteria

1. THE Dream_Cycle_DB SHALL provide a `dream_cycle_runs` table with columns: id, run_type, started_at, completed_at, explorer_output, explorer_feedback_injected, candidates_generated, candidates_accepted, candidates_deferred, candidates_rejected, and digest.
2. THE Dream_Cycle_DB SHALL provide a `dream_cycle_candidates` table with columns: id, run_id, candidate_json, operation, target_memory_id, schema_operation, individual evaluator verdicts and reasoning, final_verdict, created_memory_id, user_rejected_at, user_rejection_reason, deferred_twice_rejected, and created_at.
3. THE Dream_Cycle_DB SHALL add an `expired_at` column to the `memory_relationships` table for temporal awareness.
4. THE Dream_Cycle_DB SHALL enforce referential integrity: run_id references dream_cycle_runs, created_memory_id references memories.
5. WHEN a user rejects an accepted insight post-hoc, THE Dream_Cycle_DB SHALL record the rejection timestamp and reason without deleting the memory.

### Requirement 15: Memory Lifecycle States

**User Story:** As a knowledge system owner, I want memories to transition through lifecycle states, so that superseded and consolidated knowledge is demoted but not lost.

#### Acceptance Criteria

1. THE Orchestrator SHALL support memory lifecycle states: active, superseded, consolidated, archived, and user_rejected.
2. WHEN a memory is superseded, THE Orchestrator SHALL set its status to 'superseded' and annotate it with the supersession date, link to the new memory, and reason.
3. WHILE a memory has status 'superseded' or 'consolidated', THE memory SHALL receive moderate demotion in normal search but remain fully visible to the Explorer.
4. WHEN a user rejects a dream cycle insight, THE Orchestrator SHALL set the memory status to 'user_rejected' and store the user's reason.
5. THE Orchestrator SHALL preserve all existing relationships on superseded memories for historical context.

### Requirement 16: Error Handling

**User Story:** As a knowledge system owner, I want the pipeline to handle agent failures gracefully, so that partial failures do not corrupt data or lose completed work.

#### Acceptance Criteria

1. IF the Explorer agent crashes or times out, THEN THE Orchestrator SHALL log the error, mark the run as completed with zero candidates, and exit cleanly.
2. IF the Thinker agent fails for a single slice, THEN THE Orchestrator SHALL skip that slice, log the error, and continue processing remaining slices.
3. IF an evaluator agent crashes or times out, THEN THE Orchestrator SHALL retry it up to a bounded number of attempts; if it still fails, THE Orchestrator SHALL abort the run loudly (`aborted_early`, exit 2) rather than fabricate a verdict. A crashed evaluator returns no vote (an omission fault) and MUST NOT be recorded as REJECT; candidates already evaluated are preserved in the run's stats.
4. IF the database becomes unreachable mid-run, THEN THE Orchestrator SHALL log the error and exit with code 2.
5. IF a SUPERSEDE target memory does not exist, THEN THE Orchestrator SHALL downgrade to a CREATE operation and log a warning.

### Requirement 17: Prompt Templates

**User Story:** As a knowledge system owner, I want agent prompts stored as templates with variable interpolation, so that prompts are maintainable and consistent with the design document.

#### Acceptance Criteria

1. THE Prompt module SHALL store templates for the Explorer, Thinker, and all three evaluator roles in `src/prompts/`.
2. THE Explorer prompt template SHALL accept memory_count, date_range, feedback_injection, run_type, and optional scope as interpolation variables.
3. THE Thinker prompt template SHALL be static (no interpolation variables beyond the input data).
4. THE evaluator prompt templates SHALL accept the evaluator role, candidate JSON, and source memories content as interpolation variables.
5. THE Prompt module SHALL support scoped prompt variants for different execution modes (session_start restricts strategies, post_learn restricts scope).

### Requirement 18: Metrics and Observability

**User Story:** As a knowledge system owner, I want three tiers of metrics, so that I can measure and improve the dream cycle's effectiveness over time.

#### Acceptance Criteria

1. THE Dream_Cycle_DB SHALL compute Tier 1 process metrics per cycle: acceptance rate, acceptance rate trend, deferred-to-accepted conversion rate, Explorer strategy diversity, and cost efficiency. Tier 1 metrics are derivable from the existing `dream_cycle_runs` and `dream_cycle_candidates` tables via SQL aggregate queries — no additional storage needed.
2. THE Dream_Cycle_DB SHALL support Tier 2 engagement metrics: user rejection rate, user rejection reason clustering, and insight citation rate via access_count on dream-cycle-created memories. Tier 2 metrics require the digest UX; for v1 (static markdown), engagement tracking is limited to user rejection rate and insight citation rate.
3. THE Dream_Cycle_DB SHALL support Tier 3 downstream impact metrics: golden query extraction from accepted insights' "Questions this answers" fields for monthly retrieval quality benchmarking via `scripts/golden_queries.py`.
4. WHEN a deferred insight is rejected on its second attempt, THE Dream_Cycle_DB SHALL log it with `deferred_twice_rejected = TRUE` for Tier 1 metrics.

### Requirement 19: Scheduling and CLI

**User Story:** As a knowledge system owner, I want the dream cycle to run automatically on a weekly schedule and be triggerable from the command line, so that it operates autonomously with manual override capability.

#### Acceptance Criteria

1. THE scheduling system SHALL provide a launchd plist for weekly Sunday 4AM execution of the scheduled dream cycle.
2. THE CLI entry point (`scripts/dream_cycle_run.py`) SHALL accept a run_type argument to support all 4 execution modes.
3. WHEN run_type is 'user_triggered', THE CLI SHALL accept an optional topic scope argument.
4. THE CLI SHALL use `scripts/job_wrapper.sh` for macOS notification on failure.
5. THE CLI SHALL exit with code 0 on success, 1 on partial failure, and 2 on total failure.
