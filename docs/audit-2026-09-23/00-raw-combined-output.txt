## 1. CONTRADICTIONS

**C1 — HIGH — Two failure paths disagree about whether persisted work is reported.**
`src/dream_cycle/orchestrator.py:498-506` (Step 7 comment) promises: *"keep the candidates already evaluated so the run record reflects real persisted work (no zeroed-stats lie / orphaned accepted memories)"*. The evaluator-abort path honours this (`panel_aborted = True; break` at :531, then Step 8 runs). The spend-cap path does not: `SpendCapExceeded` from `_record_spend` propagates out of `_run_pipeline` to `run()` :327-333, which calls `complete_run(run_id, stats=_ZERO_STATS, digest="")`. Candidates and accepted *memories* are already committed to the DB, but the run row says `candidates_generated=0/accepted=0/rejected=0` — exactly the "zeroed-stats lie" the comment forbids. Same for the generic `except Exception` at :336-347.
Fix: hoist `all_candidates/accepted/rejected` into instance state (or return them from `_run_pipeline` via a result object) and complete the run with the real counts on every abort path; reserve `_ZERO_STATS` for aborts that happen before any candidate exists.

**C2 — HIGH — Per-slice candidate cap (3) contradicts the Thinker contract (2) and the budget arithmetic (2).**
`orchestrator.py:105` `MAX_CANDIDATES_PER_SLICE = 3`, with the comment at :104 "the Thinker is asked for at most 2". `src/prompts/thinker.py` says twice "Return at most 2 candidates per slice" / "Generate 0-2 candidate insights". The budget pre-check at :428 assumes exactly two new candidates: `needed = EST_THINKER_CALL_USD + 2 * EST_JUDGE_CANDIDATE_USD + …`. So a compliant-but-greedy Thinker yields 3 kept candidates while the budget reserved money for 2 — a systematic ~$0.70 per-slice underestimate against a $9 cap.
Fix: pick one number. Either set `MAX_CANDIDATES_PER_SLICE = 2` (matching the prompt) or make the budget formula use `MAX_CANDIDATES_PER_SLICE` instead of the literal `2`.

**C3 — HIGH — The "independent four evaluators" claim is violated by the grounding audit seat.**
`src/prompts/panel.py:4` and the per-call prompt at :232-234 tell every seat "Four independent evaluators … your verdict … is combined with theirs". But `orchestrator.py:103` `GROUNDING_AUDIT_ROLE = "skeptic"`, and `_ground_candidate` (:1131) audits the candidate with the *skeptic* seat, whose findings drive the revision — then `_run_pipeline` :523 asks the same skeptic to vote on the text produced from its own issue list. The skeptic votes on its own correction; independence for seat A is gone, and a 3-of-4 quorum with one correlated seat is weaker than advertised.
Fix: either use a dedicated non-voting audit role (add a `grounding` role to `VALID_ROLES`/profiles) or exclude the audit seat from the vote and tally 3 seats with an explicit threshold. At minimum stop claiming independence in the prompt.

**C4 — MEDIUM — The anchored-slice thresholds are encoded twice with a copy in raw literals.**
`src/dream_cycle/allocation.py:58-59` define `ANCHOR_ARRIVAL_SHARE = 0.6`, `ANCHOR_MIN_SOURCES = 2`, consumed by `is_anchored` (:95). `src/dream_cycle/ledger.py:125` recomputes the same predicate with hard-coded literals: `m["arrival_share"] >= 0.6 and m["source_types"] >= 2`. Changing the constant silently desynchronises the enforced budget from the reported `arrival_anchored_slices`.
Fix: have `ledger.run_metrics` import `allocation.is_anchored` (or move both constants into a shared module to avoid ledger→allocation coupling).

**C5 — MEDIUM — Semantic-memory composition limit is 4 in the prompt, 3 in the code.**
`src/prompts/explorer.py:132` "at most 4 semantic memories … per slice"; `allocation.py:64` `MAX_SEMANTIC_IN_ARRIVALS = 3`, and `compose_arrivals_slice`'s docstring (:493-499) claims the value "satisfies the evidence-independence composition rule" — i.e. the rule it cites is stated as 4.
Fix: single constant, referenced by the prompt via f-string (the prompt module already builds strings dynamically elsewhere).

**C6 — MEDIUM — Arrivals filters disagree across four call sites; the guaranteed slice can re-ingest the dream cycle's own output.**
`src/skim/store.py:31-42` (`arrivals_filter_sql`) excludes superseded rows *and* dream-cycle syntheses, because "a run must not skim what the previous run synthesised" (:19-22). `dream_cycle_db.get_recent_parent_memories` (:978-995) — the candidate pool for the *guaranteed arrivals slice* — excludes superseded but **not** dream-cycle outputs, so up to `MAX_SEMANTIC_IN_ARRIVALS` of the run's own prior insights can enter the slice as `generated:insight`. `src/db.get_arrivals_summary` (:200-245) filters neither, and `scripts/skim_probe.py:57-63` has a third hand-rolled variant.
Fix: export one filter (`store.arrivals_filter_sql`) and use it in `get_recent_parent_memories`, `get_arrivals_summary` and the probe.

**C7 — MEDIUM — Inventory header counts documents the inventory deliberately excludes.**
`orchestrator.py:706-712` builds `counts` from `get_arrivals_summary` (unfiltered, includes superseded + `generated:*`) and passes it to `allocation.render_arrivals_inventory`, whose header (:247-250) then reads "N documents across M channels; K of them were read by the skim stage". The N−K gap is partly by-design exclusions, not skim misses, so the Explorer is told the skim covered less of the window than it did.
Fix: compute the header counts from the same filtered query the skim uses.

**C8 — MEDIUM — `run_type` gating: comment says "scheduled", code says scheduled *or* session_start.**
`orchestrator.py:381-383` comment: "On a scheduled run an Explorer failure no longer aborts the night"; the condition at :387 is `if run_type not in ("scheduled", "session_start")`. Session-start runs also survive an Explorer crash and fall back to the arrivals slice, which is a different operational promise than documented (session_start is the frequency-capped briefing, with a restricted strategy set at `explorer.py:SESSION_START_STRATEGIES`).
Fix: align the comment, or restrict the fallback to `scheduled` if that was the intent.

**C9 — MEDIUM — Unknown-backend default is "has tools" in one place, "no tools" in another.**
`orchestrator._role_has_tools` (:161-166) returns `True` when `BACKEND_CAPABILITIES.get(backend)` is None ("assume MCP"), so an unknown backend gets no JSON schema and a tool-enabled Thinker call. `_skim_arrivals` (:936-941) treats `caps is None` as a *skip*. Two opposite fail-safe defaults for the same unknown condition.
Fix: one helper (`capabilities_for(role)`) that raises or returns a single explicit default.

**C10 — LOW/MEDIUM — Terminology drift: BFT / quorum / consensus / panel / acceptance.**
`src/dream_cycle/consensus.py:3-5,12-14` states the rule twice as "Lamport's 3f+1 bound with f=1 … BFT quorum 2f+1 = 3 out of 4"; `migrations/004_evaluator_d.sql:2-3` repeats it; `digest.py:32` says "passed BFT consensus (≥3/4 ACCEPT)"; `orchestrator.py:497` calls it "Step 7: Consensus Panel"; `prompts/panel.py` and `docs/PLAN-panel-acceptance.md` call it "panel acceptance" with a *graded* Standard; `scripts/panel_replay.py:275` prints "3-of-4". Four vocabularies for one 3-of-4 majority vote (and BFT is a misnomer: the seats are different prompts over correlated models, not independent replicas tolerating a Byzantine actor).
Fix: pick "panel acceptance (3-of-4 majority)" and drop the BFT framing, or keep it in exactly one docstring with an explicit caveat.

**C11 — LOW — Role→letter mapping duplicated in four places.**
`orchestrator.py:544-560` (`verdict_a` = skeptic … `verdict_d` = methodologist), `dream_cycle_db.get_evaluator_verdicts_for_run` :737-742, `feedback.py:52-57` (`evaluator_a → "Skeptic"`, `evaluator_b → "User Advocate"`), `scripts/panel_replay.py:SEAT_COLUMNS`. The label also drifts: "User Advocate" (feedback) vs "Advocate" (digest `role.capitalize()`, digest.py:141) vs `"advocate"` (prompts).
Fix: one module-level `SEAT_COLUMNS = {"skeptic": "a", …}` plus display names, imported everywhere.

**C12 — LOW — Scheduled-job comment describes the `hybrid` profile; the job exports `controlled`.**
`scripts/jobs/dream_cycle_scheduled.sh:17-19` explains the cost envelope in terms of "hybrid = Claude roles on Kiro … only the two GPT-6 Astra seats metered"; :32 exports `SECOND_BRAIN_PROFILE="${SECOND_BRAIN_PROFILE:-controlled}"`. The same comment block (:23-25) claims a cap trip means "candidates already accepted are kept, the digest is skipped" — see C1: the rows are kept but the run's stats are zeroed.

## 5. STRUCTURAL PROBLEMS AND REFACTOR SEAMS

### What `orchestrator.py` (1201 lines) actually does
Seven distinct responsibilities in one class:
1. **Run lifecycle / error funnel** — `run` (:268-347): kill switch, `SpendTracker` reset, session-start frequency cap, run-record creation, and the three top-level `except` arms.
2. **Pipeline sequencing** — `_run_pipeline` (:349-615): steps 2–9 inline, including all budget arithmetic and the verdict→DB dict assembly (:544-560).
3. **Per-role invocation + parsing** — `invoke_explorer` (:651-786), `invoke_thinker` (:962-1073), `invoke_evaluator` (:1075-1117): prompt build, invoker call, spend record, fixture capture, output coercion, dataclass construction.
4. **Attention allocation glue** — `_allocate_attention` (:788-831).
5. **Skim stage glue** — `_skim_arrivals` (:891-960), `_load_skim_records` (:833-889).
6. **Grounding audit + revision** — `_ground_candidate` (:1119-1152), `_revise_candidate` (:1154-1201), including the "sources may only shrink / relationships may only be dropped" invariants.
7. **Cross-cutting utilities** — `_as_int`, `_as_str_list`, `_unwrap_nested_candidate`, `_capture`, `_aborted_result`, `_backend_provenance`, `_skim_cap_usd`.

**Natural seams** (in dependency order, each extractable without touching the others):
- `budget.py` — `EST_*`, `GROUNDING_SPEND_SHARE`, `SKIM_*`, `_skim_cap_usd`, `_budget_remaining`, and two pure predicates `can_afford_slice(remaining, pending)` / `can_afford_candidate(remaining)`. Removes the duplicated units of P7 and makes C2 a one-line test.
- `stages/skim_stage.py` — `_skim_arrivals` + `_load_skim_records` (they already return `None`/`[]` on every failure, i.e. they are already an isolated stage).
- `stages/grounding.py` — `_ground_candidate` + `_revise_candidate` + `_unwrap_nested_candidate` (already used standalone by `panel_replay.replay_grounded`, which reaches into `orch._spend`, `orch._slice_memory_cache`, `orch._current_run_id` — a clear sign this wants to be its own object).
- `agents/{explorer,thinker,evaluator}.py` — the three `invoke_*` methods; each needs only `resolver`, `_spend`, `_capture`, `_slice_memory_cache`. The shared parts (`_record_spend`, `_capture`, `_role_has_tools`, output coercion) become a small `AgentRunner` base.
- `run_result.py` — `_ZERO_STATS`, `_aborted_result`, and the stats-merge logic; fixing C1 means this object must carry real counts through the abort paths.
- The **verdict→DB dict** block (:544-560) plus the empty-content REJECT block (:520-528) belong in `dream_cycle_db` (or a `verdicts.py`), which also kills C11.

### What `dream_cycle_db.py` (994 lines) actually does
Five unrelated concerns behind one module, all sharing only `get_connection`:
1. **Run/candidate writes** — `create_run` (:16), `complete_run` (:46), `store_candidate` (:87), `mark_user_rejected` (:400), `record_slices` (:869).
2. **Feedback reads** — `get_recent_rejections` (:151), `get_user_rejections` (:200), `get_accepted_dissents` (:241).
3. **Scheduling / stats reads** — `get_last_briefing_time` (:287), `should_run_briefing` (:311) *(business logic, not a query — it makes the 24h decision)*, `get_memory_stats` (:361), `get_strategy_usage` (:806).
4. **Metrics/eval** — `get_tier1_metrics` (:520), `get_tier2_metrics` (:627), `get_golden_queries` (:437), `extract_golden_queries` (:480) *(pure text parsing with no DB access at all — misfiled)*.
5. **Attention-ledger reads** — `get_previous_run_started_at` (:897), `get_recent_slice_memory_ids` (:924), `get_slices_for_run` (:950), plus **pass-through delegates** to `src.db` (`get_memory_provenance` :969, `get_arrivals_summary` :973) whose only purpose is "so the orchestrator reaches every attention-related query through this module (which its unit tests patch)" (:965-967).

**Natural seams:** `dream_cycle_runs_db.py` (1), `feedback_db.py` (2), `briefing.py` (3, with `should_run_briefing` moved out of the DB layer since it is a policy decision), `metrics_db.py` + `golden_queries.py` (4, and `extract_golden_queries` has no business in a DB module), `attention_db.py` (5). The delegate shim in (5) is a **test-seam artifact**: a `Protocol`-typed `DcDb` dependency injected into the orchestrator would let the delegates disappear.

## 6. CORRECTNESS RISKS

**R1 — HIGH — Spend-cap abort loses the run's accounting (see C1).** A cap trip mid-panel leaves accepted memories in `memories`, candidate rows in `dream_cycle_candidates`, and a run row claiming zero of everything. Every downstream metric (`get_tier1_metrics` acceptance_rate, `acceptance_rate_trend`, `cost_efficiency`) is computed from those run columns (`dream_cycle_db.py:558-566`) and is therefore wrong for any capped run.

**R2 — HIGH — A storage failure on one accepted candidate aborts and zeroes the whole run.** `orchestrator.py:536-563`: `check_duplicate`, `store_accepted` and `store_candidate` are called **outside** the loop's `try` (which covers only the four evaluator calls, :522-531). `storage.store_accepted` does unguarded dict indexing on LLM-supplied data — `rel["target_id"]`, `rel["relation_type"]` (:104-110) — so one malformed relationship raises `KeyError`, unwinds to `run()`'s generic handler (:336), and discards the stats for every candidate judged before it. Fix: wrap persistence per candidate; validate `relationships` entries (the revision path at :1177-1181 already filters by `target_id` but never checks `relation_type`).

**R3 — HIGH — Nothing prevents two concurrent dream-cycle runs, and the spend cap is per-process.** `run()` creates a run row unconditionally (`:314`); there is no advisory lock or lockfile — contrast `scripts/redistill_capped.py:_acquire_lock` (:208-221), which does exactly this for a lesser job. A launchd run overlapping a manual `dream_cycle_run.py` gives two independent `SpendTracker`s, i.e. 2×$9, plus interleaved `record_slices` DELETE/INSERT and duplicate skim work (mitigated only by `upsert_skim`'s `ON CONFLICT`). Fix: `pg_try_advisory_lock` on a dream-cycle key, or reuse the lockfile pattern.

**R4 — MEDIUM — Skim sub-cap is checked only between documents, so one call can overshoot it.** `runner.py:186-192` tests `result.cost_usd >= cap_usd` at the top of each iteration; a single large document can push the pass past the sub-cap by its own full cost. With `max_doc_chars = 120_000` (:47) and Nova 2 Lite at $0.33/M input, the overshoot is bounded (~$0.01) — but the *run* cap has the same shape at a much larger scale: `_record_spend` is called after each Thinker/evaluator call, so a single Astra call (bounded only by `BEDROCK_MAX_TOKENS`, ~$0.90 per the job script) can exceed the cap before anything notices. Fix: pre-flight estimate from prompt size before the call, not only post-hoc.

**R5 — MEDIUM — The budget soft-stop is a no-op on unmetered backends, silently.** `_budget_remaining` (:186-194) returns `cap − total_usd` from *real* usage only; `_record_spend` (:168-184) returns early when `usage` is not a dict. With Kiro seats the total stays 0, so `remaining` is always ≈ cap and no slice or candidate is ever deferred — documented in the docstring, but it means the `hybrid`/Kiro profile has *no* budget control at all, and the live `controlled` profile's control is partial (only the metered seats count).

**R6 — MEDIUM — Broad `except Exception` swallows programming errors in three stages that are supposed to only swallow *infrastructure* errors.** `_allocate_attention` :826-829 ("Attention allocation failed (non-fatal); using Explorer slices as-is") will also hide a `KeyError`/`TypeError` in `enforce_budget` or `slice_metrics` — the run then proceeds unbudgeted with no ledger and one WARNING. Same shape at `_load_skim_records` :864-868, `_skim_arrivals` :954-957, `invoke_explorer`'s manifest block :737-738, `digest.py:94-95`. Fix: catch `(psycopg2.Error, OSError, ValueError, KeyError)` explicitly, or re-raise on `AttributeError`/`TypeError`; at minimum log at ERROR so a broken stage cannot run silently for weeks.

**R7 — MEDIUM — One genuinely silent swallow.** `digest.py:59-62`:
```python
try:
    feedback_injected = dream_cycle_db.was_feedback_injected(run_id)
except Exception:
    pass
```
No log at all; the digest then asserts "No feedback was injected (no prior rejections or first run)" (:107-108) — a false statement produced by a DB error.

**R8 — MEDIUM — `except …: continue` hides real failures in the two hot loops.** `orchestrator.py:456-460` ("Thinker failed for slice '%s', skipping") turns a systematic Thinker/backend breakage into N quiet slice skips and a healthy exit 0, since `exit_code_for` keys only on `aborted_early` (`scripts/dream_cycle_run.py:90-103`). Same in `runner.py:207-212` and `:245-250`: a model failure and a *storage* failure both increment `result.failed`, so a fully broken `memory_skim` write path reports "N failed" and the run completes normally. Fix: distinguish call failures from store failures in `SkimResult`; trip a threshold (e.g. >50% of slices/documents failing ⇒ abort loudly).

**R9 — MEDIUM — Retry counts as "bounded" only per seat; the panel's worst case is 12 calls per candidate.** `EVALUATOR_MAX_ATTEMPTS = 3` with `EVALUATOR_BACKOFF_S * attempt` (:57, :641-644) applies independently to each of the four seats, and `_invoke_evaluator_safe` retries on `ValueError` too — which `invoke_evaluator` cannot raise (it defaults to `verdict="REJECT"` on unparseable output, :1104-1112), so that arm is effectively unreachable. Meanwhile `_ground_candidate` and `_revise_candidate` get **no** retry (:1131, :1160) — an inconsistent resilience policy across calls of identical cost. Note the one thing that is right: `SpendCapExceeded` is deliberately not a `RuntimeError` (`cost.py:164-166`) so the retry loop cannot swallow it.

**R10 — MEDIUM — Digest files collide within a day.** `digest.py:175-176` writes `logs/dream-cycle-digest-{YYYY-MM-DD}.md` with `write_text` — a second run on the same date (scheduled + user_triggered, or a re-run) silently overwrites the first, and both run rows point at the same path. Fix: include the run id or a timestamp.

**R11 — LOW/MEDIUM — Persisted slice order ≠ judging order ≠ `explorer_output` order.** `record_slices` persists positions in pre-order (:820, inside `_allocate_attention`), then `order_slices` reorders the list (:416-418) and `complete_run`'s `explorer_output` is serialised from the *reordered* list (:606). `self._slice_rows` is not reordered, so after :417 it no longer aligns with `slices`. Nothing currently reads it afterwards, but the invariant "rows[i] describes slices[i]" that `order_slices` itself depends on (:551-553) is silently broken from that line on — a trap for the next edit.

**R12 — LOW/MEDIUM — Non-deterministic tie-breaking in stratified allocation.** `allocation.allocate_stratified` :345-356 iterates `sorted(channels, key=lambda c: -channels[c])` with no secondary key, so channels with equal counts are ordered by dict-insertion, i.e. by DB row order. `rank_skim_records` (:203-221) does this correctly (`key=lambda c: (-len(...), c)`), as does `render_arrivals_inventory` (:252). Fix: add the name as a tiebreaker in `allocate_stratified` for reproducible slices.

**R13 — LOW — `check_duplicate` can miss a near-duplicate by construction.** `storage.py:127-129`: `search_similar(embedding, limit=5, status="active")`, then chunk rows (`parent_id is not None`) are *skipped after* the limit is applied — so if the top 5 neighbours are all chunks, a parent duplicate at rank 6 is never seen and the insight is stored twice. Fix: filter chunks in SQL, or over-fetch.

**R14 — LOW — Unbounded evaluator prompt via `format_sources_for_evaluator`.** See I10: per-memory caps apply (4,000 chars) but there is no total cap, unlike `build_packet`'s 120,000. A candidate citing 40 sources yields ~160K chars of prompt at Astra input rates, per seat, per candidate.

**R15 — LOW — `storage.store_accepted` UPDATE path tolerates a missing target.** `:60-83`: when `get_memory(target_memory_id)` returns `None`, `existing_metadata` becomes `{}` and `update_memory` is still called on the non-existent id; only the SUPERSEDE path checks for a missing/already-superseded target (:85-92). Fix: apply the same downgrade-to-CREATE guard to UPDATE.

## 5. CORRECTNESS RISKS

### R1 — `chunk_by_section` emits a single unbounded chunk for Slack and YouTube documents. **High.**
`src/ingest.py:63-102`. Splitting is `re.split(r'\n(?=##\s)', body)`; with no `##` headers it falls back to `body.split("\n\n")`. Slack renders its day body with `"\n".join(lines)` (`slack.py:141`) and YouTube renders transcripts with `"\n".join(out)` (`youtube.py:138`) — **neither ever produces a blank line**. So `paragraphs` is a single element, the `if current_len + len(para) > max_chunk_chars and current` guard is False on the first iteration (`current` is empty), and the merge loop returns `[body]`. Result: one chunk of up to 60 000 chars for Slack (`MAX_DOC_CHARS`, `slack.py:57`) and of unbounded length for a YouTube transcript, handed straight to `generate_embedding` (`ingest.py:203`). `max_chunk_chars=4000` is silently not enforced for the two highest-volume channels. Fix: make `chunk_by_section` hard-split any section exceeding `max_chunk_chars` on line boundaries, and add a property test asserting `max(len(c) for c in chunks) <= max_chunk_chars * 1.1` for header-less, blank-line-free input.

### R2 — Partial document writes are committed and then permanently skipped. **High.**
`src/db.py:92-106` commits every `create_memory` in its own transaction. `ingest_content` (`ingest.py:174-209`) commits the parent, then commits each chunk in a loop. If chunk 3 of 9 raises (Bedrock throttle, oversized input per R1), the parent and chunks 1-2 are already durable, the `source_url` is now in the table, and `ingest_batch` counts `failed` (`ingest.py:236-238`) — but the **next** run reads that `source_url` from `get_processed_source_urls` and skips it (`ingest.py:226-228`). The document stays permanently half-embedded with no marker. Contrast `codex.py:186-200` / `_store_semantic_result`, which wraps everything in one transaction with `rollback()`. Fix: wrap parent+chunks in one transaction (a `create_memory_tree(conn, …)` taking an explicit connection), or write the parent last, or record `metadata.chunks_expected` and treat a mismatch as not-yet-captured.

### R3 — Empty-timestamp collapse in Outlook source URLs — same shape as the crawlee `"" in text` bug. **High.**
`outlook.py:106-110`: `received = (msg.get("receivedDateTime") or msg.get("sentDateTime") or "")[:19]` → when both are absent the URL is `outlook://mail//<hash(subject|sender)>`. Every body-less-timestamp message with the same subject+sender collapses onto **one** `source_url`; the first wins and the rest are silently dropped as "already captured" (`outlook.py:216-218`). `event_source_url` (`outlook.py:152-154`) has the identical `or ""` on `ev["start"]`. Additionally, the hash has no body component, so two genuinely different mails sent in the same second by the same sender with the same subject collide by design. Fix: refuse to build a URL when the timestamp is empty (raise/skip and count it), and include a body digest in `_hash`.

### R4 — Identity by truncated prefix: `conv_id[:12]`. **High.**
`chat_extract.py:94` truncates the CLI conversation id to 12 characters for the staging filename; `batch_ingest_staged.py:67-69` then derives `source_url = f"chat://{f.stem minus prefix}"` from that filename. Two CLI sessions sharing a 12-char prefix produce the same `source_url`; the second is counted as `skipped` and its file is moved to `staging/ingested` (`batch_ingest_staged.py:71-77`), i.e. deleted-by-move with no error. The IDE side does not truncate (`chat_extract.py:83`), so the two halves of one channel have different identity strength. Fix: use the full id in the filename (or a hash of it) and assert `len(set(source_urls)) == len(files)` before ingesting.

### R5 — Containment tests used for identity/eligibility decisions. **Medium-High.** (The crawlee-bug family.)
- `scripts/scrape_bookmarks.py:21-30`: `SKIP_PATTERNS.search(u)` applies bare substrings `login`, `signin`, `isengard`, `phonetool`, `sim.amazon`, `issues.amazon`, `cr.amazon`, `code.amazon` **against the whole URL**, unanchored. Any URL containing "login" in a path or query is dropped — e.g. an article at `…/blog/how-single-signin-works`. `.` is unescaped throughout, so `sim.amazon` also matches `simXamazon`. This filter is then imported and applied to *all* browser history by `browser.py:100,150`, so the over-skip propagates to a second channel.
- `browser.py:200-203` `canonical_url`: `k.lower().startswith((… "ref" …))` drops any parameter whose name *begins with* `ref` — `refresh`, `reference`, `referrer`, `refinement`. Two distinct pages differing only in such a parameter collapse to one `source_url`, so one of them is never captured.
- `scrape_bookmarks.py:51-55` `load_indexed_urls`: `re.finditer(r"\((https?://[^)]+)\)", f.read())` over the **entire** `index.md` text — not per row and not scoped to the source cell. Any URL appearing inside a summary link or a note is treated as already-indexed, so it is never scraped. This is the inverse failure of the crawlee bug: the fixed parser (`crawlee.py:80-105`, `build_source_map` at `crawlee.py:193-222`) is now rigorous, but the *bookmark* side still reads the same file with the old loose regex. **These two readers of `index.md` must be unified.**
- `slack.py:243-249` `_dm_inactive_for`: `return la < since` compares a server-supplied `lastActivity` string lexicographically against a `%Y-%m-%dT%H:%M:%SZ` string. Any format difference (offset instead of `Z`, epoch ms, missing seconds) makes the comparison meaningless and silently skips the DM for the whole window, with no log line.
- `cli_chat.py:130-134` `is_automated_conversation`: `any(m in first[:120] for m in _AUTOMATED_MARKERS)` — a human message that merely quotes `"Run type:"` in its first 120 chars is discarded as an automated sub-agent conversation.
- `distill_sessions.py:222` `{u.rsplit("#", 1)[0] for u in already}` — recovers the session key by splitting on the last `#`; any `source_url` containing `#` (Codex segments use `#segment-N`, `codex.py:~960`) would be mis-keyed if ever routed here.

### R6 — Swallowed exceptions that hide real failures. **Medium-High.**
- `ingest.py:105-146` `_discover_relationships`: four bare `except Exception: pass`. The first block calls `generate_embedding(body)` on the **entire document body** (`ingest.py:108`) — a second, larger embedding call per document that no channel knows about. For an oversized body (R1) it raises, the exception is swallowed, and relationship discovery silently never runs for exactly the largest documents. Invisible to every monitor. Fix: `logger.warning` with the source_url, and count discovery failures in the stats dict.
- `browser.py:99-103` `_import_bookmark_filters`: a broad `except Exception` returns a drastically weaker fallback (`INTERNAL_DOMAINS = re.compile(r"\.amazon\.com")`) with the `# pragma: no cover` comment "the scraper is part of this repo". If the import ever breaks, internal `*.a2z.com` / `*.aws.dev` URLs are reclassified `public` (`browser.py:156-158`) and sent to Crawlee (`browser.py:330`) — a confidentiality regression, silently. **This is the highest-consequence swallowed exception in the layer.**
- `chat_extract.py:61-65` `except Exception: ingested = set()`: a DB hiccup means the entire chat history re-stages. The comment calls `batch_ingest_staged` the "downstream dedup backstop", which is true for the DB, but the staging directory fills with thousands of files first.
- `ingest_chats.py:56-59`: bare `except:` around the rename (dead script, but it is a bare except).
- `crawlee.py:203-217` / `find_unindexed_output_files`: file reads are unguarded inside a generator (`crawlee.py:281`, `crawlee.py:322`) — one unreadable file aborts the whole `parse_all` iteration mid-stream, and `crawlee_ingest.py`'s per-item `try` (`:63`) does not cover the generator's own `next()`.

### R7 — Silent no-ops that exit 0 and are invisible to monitors. **High.**
- `browser.py:291-293`: Chrome History missing → `logger.error` + zeros; `main()` (`browser.py:346-357`) returns `None`; `capture_browser.sh:8` `exec`s it → **exit 0**. `job_wrapper.sh:40-45` only notifies on non-zero, so a permanently relocated Chrome profile produces a green job forever.
- `youtube.py:167-169`: DB unreachable → `logger.error` + `return stats`; `main()` discards the return (`youtube.py:221-222`) → exit 0.
- `youtube.py:184-190`: in `--dry-run`, `stats["processed"] += 1` — a dry run reports the same counter a real run does, so a log line cannot distinguish them.
- `scripts/jobs/ingest_staged.sh:46-49,80`: the crawlee failure is logged (`Crawlee ingest FAILED`) but the script ends with an unconditional `exit 0`, and the status file it writes for monitoring (`ingest_staged.sh:65-74`) contains no crawlee-failure field — only a before/after row count (`ingest_staged.sh:43-52`). A crawlee ingest that fails every night looks identical to one that finds nothing new.
- `chat_extract.py:69,102-108`: `errors` is incremented and printed, then the process exits 0.
- `scrape_bookmarks.py:126-163`: `main()` prints and never exits non-zero; the plist routes it through `job_wrapper.sh`, whose notification therefore can never fire. A 1-hour Crawlee timeout (`scrape_bookmarks.py:120-121`) prints `⚠` and returns normally.
- `scripts/jobs/qd_sync.sh:19-24`: `set -euo pipefail`, six python scripts chained with no wrapper. The first failure aborts the rest of the chain, and `com.second-brain.qd-sync.plist` does **not** use `job_wrapper.sh` (unlike every other job), so there is no notification — only a line in `logs/qd-sync-<date>.log`. The completion line (`qd_sync.sh:27`) is never reached, which is the only signal.
- **Monitor/writer mismatch:** `tests/test_monitor_jobs.py:283,286` asserts freshness checks for `quick_desktop_synth`, but I found **no writer** of `quick_desktop_synth` in `src/` or `scripts/` (the QD writers emit `quick_desktop_chat`, `quick_desktop_doc`, `quick_desktop_decision`, `quick_desktop_feed`, …). Either the monitor watches a source_type nothing produces (permanently red or permanently ignored) or the writer lives outside this repo. Flagged for verification.

### R8 — Timezone handling is inconsistent and in places unsound. **Medium.**
- **Local vs UTC day boundaries differ by channel.** Slack and Browser use completed *local* days (`slack.py:160-172`, `browser.py:210,224-227`); Outlook uses a rolling *UTC* window (`outlook.py:277-279`); the chat parsers stamp `Date:` from a *UTC* conversion of an epoch (`cli_chat.py:133-136`, `ide_chat.py:143-149`). The same afternoon can therefore be filed under two different dates depending on which channel captured it, which breaks any date-joined retrieval.
- **Fixed-offset tz captured at call time.** `slack.py:168` and `browser.py:224` both do `tz = datetime.now().astimezone().tzinfo`, producing a *fixed-offset* tzinfo, then `datetime.combine(day, time.min, tzinfo=tz)`. On a DST-transition day the computed midnight boundary is off by one hour, so one hour of messages/visits is attributed to the wrong day — and because both channels key dedup on the day URL, the lost hour is never re-read.
- **Unit-guessing heuristic.** `ide_chat.py:143-146`: `file_timestamp / 1000 if file_timestamp and file_timestamp > 1e12 else file_timestamp or 0` — a milliseconds/seconds guess by magnitude. A missing `start_time` silently falls through to `datetime.now()`, dating an old chat as today.
- `ingest_qd_chats.py:43` assumes `session["created_at"]` is seconds with no validation.
- **Codex is the only channel that enforces awareness** (`agent_tasks.py:14-17` `_aware`, raising on naive datetimes; `codex.py:210-212` rejects a naive `now`). Every other channel accepts whatever the source provides.

### R9 — Cursor-loop spin risk. **Low.**
`slack.fetch_day:227-241` and `outlook.collect_mail:206-222` / `collect_calendar:225-247` advance on a server-supplied token and break only when the token is absent. A server that echoes the *same* token with `hasMore: true` re-fetches the same page; the loops terminate only because of the `MAX_MESSAGES_PER_DAY` / `max_per_folder` / `max_events` counters. There is no "token did not change" guard and no log when the ceiling is hit, so a truncated capture is indistinguishable from a complete one. I found **no genuinely unbounded retry loop** in the layer; Codex's semantic retry is explicitly bounded and persisted (`codex.py:471-520`).

### R10 — `capture_api` has no dedup and no chunking. **Medium.**
`capture_api.py:103-118` `_store_memory` calls `create_memory` unconditionally. Two identical POSTs create two rows; there is no `source_url` uniqueness check and `source_url` may be `NULL` (`capture_api.py:63`). Content up to 100 000 chars (`capture_api.py:59`) is embedded as a single vector with no chunking, so an API-captured document is structurally unlike the same document captured by any collector, and is unreachable by chunk-level vector search.

### R11 — `preflight` exists for Slack only. **Medium.**
`slack.py:170-190` is the documented fix for the 2026-09-20/21 silent auth failure, and `slack.py:320-322` correctly refuses to attempt the capture when it fails. Outlook has no equivalent: a stale Graph token is only discovered after `collect_mail` has begun (`outlook.py:291`), so mail pages may already be half-processed when the run aborts. Because `ingest_batch` is called only after `collect` returns (`outlook.py:304-311`), a mid-collection auth failure discards **all** rendered items for that run rather than ingesting what was collected.

## 6. REFACTOR SEAMS

The code already converged on a de-facto contract. Nine channels independently implement the same five steps: **preflight → enumerate a window → render `(source_url, markdown)` → ingest via `ingest_batch` → map an outcome to an exit code.** Slack and Outlook have all five; the others have a subset.

### Proposed interface

```python
# src/capture/framework.py  (proposed — does not exist)
class CaptureChannel(Protocol):
    source_type: str                     # canonical taxonomy value, single definition site
    def preflight(self) -> tuple[str, str]:      # ("ok"|"auth"|"transport"|"error", detail)
    def window(self, days_back: int) -> Window   # completed-local-days OR rolling-UTC, declared explicitly
    def collect(self, w: Window, already: set[str]) -> Iterable[CapturedDoc]
    # CapturedDoc = (source_url: str, markdown: str); source_url validated non-empty + scheme-checked

def run_channel(ch, *, days_back, dry_run) -> int:   # the shared runner
    # 1. already = get_processed_source_urls(ch.source_type)
    # 2. kind, detail = ch.preflight();  non-ok -> CaptureFailure -> report_failure -> exit 3/4/1
    # 3. items = ch.collect(...);  assert every source_url non-empty, scheme-valid, unique in batch
    # 4. dry_run -> uniform {"dry_run": True, "would_ingest": n};  else ingest_batch (one txn per doc)
    # 5. uniform summary line + uniform "captures_this_cycle: <channel>=<n>" + exit code
```

Three pieces move out of the channels into shared modules:
- `src/capture/render.py` — `header(title, source_url, type, date, **extra)` with a **canonical, underscore-only** key vocabulary (fixes the `thread replies` / `video id` / `raw visits` spellings) and one `html_to_text` (retiring D6's crude copy).
- `src/capture/window.py` — `completed_local_days()` and `rolling_utc_window()`, DST-correct via a real zoneinfo tz rather than a snapshotted fixed offset (fixes R8, retires D3/D4).
- `src/ingest.py` — `ingest_document(conn, …)` writing parent+chunks in **one** transaction (fixes R2) and a `chunk_by_section` that hard-splits oversized sections (fixes R1).

### Per-channel disposition

## 5. DUPLICATION — what the base should own vs what it owns today

The two family bases (`AgenticCliInvoker`, `DirectApiInvoker`) are genuinely good factorings within their family, but they duplicate each other, and `base.py` owns almost nothing of the shared template.

**P-1 (HIGH) — the metrics dict and the metrics lifecycle are implemented twice.** `AgenticCliInvoker._init_metrics` (agentic_cli.py:280-315) and `DirectApiInvoker._init_metrics` (direct_api.py:175-207) build near-identical dicts with **divergent key names for the same quantity**: the CLI family writes `latency_s` (agentic_cli.py:190) while the direct family writes `duration_s` (direct_api.py:169). Both also write `usage_source`, `success`, `error`, `input_chars`, `output_chars`, `model`, `stage`, `run_id`. Any cross-backend latency analysis over `logs/llm_metrics/*.jsonl` silently sees two schemas. Also `_record_metrics` / `_metrics_dir` are defined identically in both (agentic_cli.py:267-278 vs direct_api.py:219-226). **The base should own:** one `_init_metrics`, one key vocabulary, one `_record_metrics`/`_metrics_dir`. **It owns today:** only `_write_metrics_line` and the `METRICS_DIR` constant (base.py:35-53).

**P-2 (HIGH) — the JSON-parse-with-metrics wrapper is duplicated verbatim.** `_parse` in agentic_cli.py:245-253 and direct_api.py:209-217 are the same six lines (try `parse_json_output`, on `ValueError` set `metrics["error"] = "json_parse_failed"`, log, re-raise); only the log format string differs. Both then re-bind `parse_json_output = staticmethod(...)` (agentic_cli.py:86, direct_api.py:77), and `KiroInvoker` binds it a *third* time (kiro.py:105). **The base should own** `_parse`.

**P-3 (MEDIUM) — the tolerate-and-warn "metered but no usage" path exists in three copies with three different warning texts.** `DirectApiInvoker._warn_missing_usage` (direct_api.py:228-245), `ClaudeCodeInvoker._extract_usage`'s warning (claude_code.py:378-390), `CodexInvoker._extract_usage`'s warning (codex.py:414-425). All three return `(None, "estimate")` and all three say roughly "metered backend, real usage expected, absent". Only the direct family has it as a reusable helper. **The base should own** `_warn_missing_usage`.

**P-4 (MEDIUM) — token accounting is done in three places with three key spellings.** The adapters normalise usage into camelCase (`inputTokens`) for Bedrock (bedrock.py:585-592) but pass provider snake_case straight through for Claude Code (claude_code.py:361-376) and Codex (codex.py:398-411); `cost.py:_tokens` then papers over both by trying alternative spellings (cost.py:139-146, 163-168). Separately, the CLI base computes char/4 estimates unconditionally (agentic_cli.py:191-192) even for metered backends that reported real counts. **The base should own** one `normalize_usage(provider_usage) -> dict` returning a single canonical shape, so `cost.py` stops guessing key names.

**P-5 (MEDIUM) — USD math has two entry points with different semantics.** `SpendTracker.record` (cost.py:203-225, enforces the cap, increments counters) and bare `estimate_cost_usd` (cost.py:149-181, no cap, no counters). `src/skim/runner.py` uses *both on the same call*: `record_spend(model, usage)` normally (runner.py:216) and `estimate_cost_usd(model, usage)` in the `SpendCapExceeded` branch (runner.py:219) so the last, cap-breaching call still gets added to `result.cost_usd`. Correct, but it means one call can be priced twice by two different functions. `scripts/panel_replay.py:174` uses `tracker.record` directly. **The base/cost module should own** a single `price_and_record(model, usage) -> (cost, capped)` that never needs a second call.

**P-6 (MEDIUM) — `_record_call_metrics` is defined three times.** `base.py:45` (`_write_metrics_line`, canonical), `agentic_cli.py:58-66` (wrapper reading the module-global `METRICS_DIR`), `kiro.py:61-66` (another wrapper for the same reason). All three exist to keep monkeypatch targets alive (C-8).

**P-7 (LOW) — timeout handling is split.** The CLI family maps `subprocess.TimeoutExpired` → `TimeoutError` in `_run_subprocess` (agentic_cli.py:198-224); the direct family relies on the adapter's `_map_exception` to map `ReadTimeoutError`/`ConnectTimeoutError`/`ModelTimeoutException` (bedrock.py:639-651, 657-660). Nothing guarantees a new adapter maps timeouts at all — `DirectApiInvoker._map_exception` defaults to returning the exception unchanged (direct_api.py:271-279), so a new direct adapter silently violates the documented `TimeoutError` contract (base.py:124-127).

## 6. COST ACCOUNTING INTEGRITY

The happy path, end to end:

1. Adapter extracts usage. Bedrock normalises Converse `usage` to camelCase plus `cacheReadInputTokens`/`cacheWriteInputTokens` and copies the **served** `serviceTier.type` (bedrock.py:584-600). Claude Code copies the envelope's `usage` and folds in `total_cost_usd` (claude_code.py:361-376). Codex parses `--json` usage events (codex.py:398-411).
2. `orchestrator._record_spend(role, result)` reads `result["usage"]` and calls `self._spend.record(self.resolver.spec_for(role).model, usage)` (orchestrator.py:182-196).
3. `SpendTracker.record` → `estimate_cost_usd(model, usage)` (cost.py:213). If the provider reported `total_cost_usd`, that wins outright (cost.py:160-162). Otherwise tokens × `price_for(model, usage["serviceTier"])` / 1e6, with cache reads at a model-specific fraction and cache writes at 1.25× input (cost.py:95-105, 170-181).
4. Total accumulates; `SpendCapExceeded` is raised *after* counting the offending call (cost.py:220-225) and deliberately does not subclass `RuntimeError` so the evaluator retry loop cannot swallow it (cost.py:183-185).

This is a sound design. The integrity problems are at the edges:

**G-1 (CRITICAL) — two paths spend without recording anything.**
- `src/express.py:481-490` constructs `AgentInvoker()` and invokes with no tracker anywhere in the call chain. On Kiro that is credits, not dollars — but the same code will bill real dollars the moment the Express editor is moved onto a metered backend, and there is no tracker to catch it.
- `src/capture/codex.py:205-212` invokes the resolved *thinker* — which under `controlled` is `bedrock/global.anthropic.claude-opus-5` at $5/$25 per 1M — and never touches a `SpendTracker`. This is a metered Bedrock call, made once per chat-session segment, with no cap and no ledger entry. It runs nightly via `scripts/jobs/codex_capture.sh`. This is the most serious cost finding: unbounded metered spend on the most expensive configured Claude model.
Fix: make the tracker a required constructor argument of any code path that resolves an invoker, or move the spend check into `Resolver.invoker_for` by wrapping the returned invoker in a metering decorator so it is impossible to invoke unmetered.

**G-2 (HIGH) — a zero-cost metered call is invisible.** `SpendTracker.record` returns early when `cost == 0.0`, *before* `self.calls += 1` (cost.py:210-212). So a metered call whose provider reported `total_cost_usd: 0.0`, or whose usage block parsed to no recognisable token keys, increments neither `calls` nor `total_usd` and produces no log line (orchestrator.py:191-196 only logs `if cost`). `tests/test_cost.py:121-122` confirms unparseable usage prices at 0. The run then reports fewer metered calls than it made. Fix: count the call unconditionally; track `calls` and `unpriced_calls` separately.

**G-3 (HIGH) — provenance and pricing both use the *requested* model, not the served one.** `_record_spend` prices against `self.resolver.spec_for(role).model` (orchestrator.py:190), and `_backend_provenance` records the same (orchestrator.py:219-225). When the CLI ignores `--model` — the documented kiro-cli 2.22 behaviour (backends.toml:105-109) detected by `_note_model_honored` (agentic_cli.py:228-243) — the served model differs from the priced model, and the warning is only a log line plus a metrics flag. A Sonnet-5 request served as Fable 5.1 would be billed at Sonnet-5's $2/$10 instead of $10/$50: a 5× understatement, and the cap would not trip. Fix: have `_extract_usage` return the served model id when the provider reports one, price on that, and treat `model_honored == False` as fatal for metered roles.

**G-4 (MEDIUM) — unknown models are billed at a ceiling that is no longer the ceiling.** `_CEILING_IN, _CEILING_OUT = 10.0, 50.0` (cost.py:75) equals the most expensive *known* row (Fable 5.1 and GPT-6 Astra, cost.py:45, 53). The comment calls it "Conservative … (= the most expensive known tier)" — true only as long as nothing pricier is ever configured, and the `DIGEST_MODEL` override (weekly_digest.py:65) plus `panel_replay --model-override` (panel_replay.py:121) both let an operator name an arbitrary model. Fix: set the ceiling to a genuine multiple of the dearest known row, or refuse to run on an unknown model rather than guessing.

**G-5 (MEDIUM) — the Flex discount depends on a field only one adapter populates.** `estimate_cost_usd` reads `usage["serviceTier"]` (cost.py:172) and Bedrock is the only adapter that sets it (bedrock.py:595-599). That is correct today, but note the failure direction: if Converse ever omits `serviceTier` from the response, the skim silently prices at the *standard* Nova rate (2× the Flex rate, cost.py:62 vs 71) — conservative, so it fails safe, but it will overstate skim cost and can trip the $1.00 sub-cap early (`_skim_cap_usd`, orchestrator.py:130-147).

**G-6 (MEDIUM) — three independent caps with no single accounting view.** `SECOND_BRAIN_RUN_COST_CAP_USD` default $5.00 (cost.py:39), the skim sub-cap `SKIM_SPEND_CAP_USD = 1.00` bounded to 15% of the run cap (orchestrator.py:111-112, 130-147), and the digest cap `DEFAULT_DIGEST_CAP_USD = 0.25` (weekly_digest.py:80). The two comment-level cost estimates in the config also disagree with the code: `controlled` says "≈ $3-4/run … under the $6/run cap" (backends.toml:117-119) but the code's default cap is $5.00 (cost.py:39), and `bedrock` says "Estimated ≈ $1.60/run" (backends.toml:75) while `hybrid` says the all-Bedrock profile is "≈ $7.50" (backends.toml:88) — two different figures for the same profile, one of them above the cap. Fix: one cap constant, documented in one place, with the per-stage sub-caps derived from it.

**G-7 (LOW) — Kiro is correctly exempt but the exemption is stated as if it were free.** `KiroInvoker._extract_usage` returns `(None, "estimate")` (kiro.py:211-216), `record` therefore contributes nothing, and `_budget_remaining` notes "With an all-Kiro profile nothing is metered … the cap binds only where usage is real" (orchestrator.py:198-203). Accurate as dollars, but it means the `laptop` and `hybrid` profiles have **no spend ceiling of any kind** and no per-call cost record — so the profiles that violate the corpus rule are also the ones with no cost telemetry.

## 1. SCHEMA VS CODE DRIFT

### 1.1 Live FTS index name exists nowhere in the repo — HIGH
`migrations/001_initial_schema.sql:36` is `CREATE INDEX ON memories USING gin (search_vector)` with no name, so Postgres auto-names it `memories_search_vector_idx`. That is exactly what `memory_bank_test` has. Live `memory_bank` instead has **`idx_memories_search_vector`** (100 MB, 94 scans). The string `idx_memories_search_vector` appears in **no** file under `migrations/`, `src/`, `scripts/`, `tests/`, or `docs/` — it was created or renamed out-of-band.

Evidence: `\d memories` on `memory_bank` vs `pg_indexes` on `memory_bank_test`; `grep -rn idx_memories_search_vector migrations scripts src tests docs` → no matches; no `ALTER INDEX … RENAME` in migrations (the only rename in the repo is `scripts/jobs/reindex_embedding.sh:29`, for the *embedding* index).

Impact: a rebuild from migrations produces a differently-named index than production. Any future `DROP INDEX idx_memories_search_vector` is a silent no-op on a fresh database — the same failure mode `migrations/009_hnsw_recall.sql:19-20` already had to defend against for the HNSW index.

Fix: name the index explicitly in 001 and add an idempotent migration 015: `ALTER INDEX IF EXISTS memories_search_vector_idx RENAME TO idx_memories_search_vector;`.

### 1.2 Migration 009 hardcodes the database name and mutates production from the test suite — HIGH
`migrations/009_hnsw_recall.sql:27`: `ALTER DATABASE memory_bank SET hnsw.ef_search = 200;`

`tests/conftest.py:84-101` (`_apply_migrations`) applies **every** `migrations/[0-9]*.sql` to the test database unconditionally. Statement 009:27 names `memory_bank` explicitly, so running it while connected to `memory_bank_test` alters **production** configuration.

Evidence: `pg_db_role_setting` shows `hnsw.ef_search=200` on `memory_bank` and `second_brain_codex_test` but **not** on `memory_bank_test`, even though `memory_bank_test` has `idx_memories_embedding` with `{m=32,ef_construction=200}` — i.e. the rest of 009 did run there.

Two consequences: the test suite issues an `ALTER DATABASE` against production, and recall-sensitive tests run at the default `ef_search=40` while production runs at 200, so `tests/test_rerank_drift.py` measures a different retrieval regime than it claims to guard.

Fix: `DO $$ BEGIN EXECUTE format('ALTER DATABASE %I SET hnsw.ef_search = 200', current_database()); END $$;`.

### 1.3 Ledger state
`memory_bank.schema_migrations` — 14 rows, `001_…` through `014_…`, exactly matching the files on disk. `000_migrations_table.sql` is absent by design (`migrations/migrate.sh:19` skips it). **No drift.**

`memory_bank_test.schema_migrations` — **0 rows**, while all 11 tables and 13 `memories` indexes exist. MEDIUM. Cause: `tests/conftest.py:84-101` applies the files directly and never writes to `schema_migrations`. Nothing can determine which migrations the test database has. ## 2. DB ACCESS STYLES — five distinct ways

**Style 1 — pooled context manager, function-owns-connection (canonical).** `src/db.py`, `src/search.py`, `src/skim/store.py`, `src/dream_cycle_db.py`. `with get_connection() as conn: with conn.cursor(…) as cur:`, `%s` params, explicit `conn.commit()` on writes, reads never commit.

**Style 2 — cursor injection.** `src/express.py` `_gather_*(cur, …)` at lines 165, 229, 272, 314, 340, 571 receive a cursor from `compose_briefing`'s single connection (375-382). Different ownership model. Worse: `load_prefs()` is called at `express.py:385`, **after** that `with` block closes, opening a second connection for the same logical operation.

**Style 3 — injected connection factory with row locking and manual rollback.** `src/capture/codex.py:218` takes `connect=db.get_connection`; uses `SELECT … FOR UPDATE` (526/531, 761, 922) and explicit `connection.rollback()` (591, 649, 781, 1067). The only place in the codebase with real row locks.

**Style 4 — raw `psycopg2.connect` with `autocommit=True`, bypassing the pool.** `tests/conftest.py:63-71`.

**Style 5 — shell/psql.** `migrations/migrate.sh`, `scripts/jobs/reindex_embedding.sh`.

**Cursor factories:** default tuple cursor for writes and scalar reads (`db.py:96,156,245,307`; `search.py:342`) vs `RealDictCursor` for row reads (`db.py:112,122,191,…`). Two row shapes inside one module — `db.py:100` indexes `cur.fetchone()[0]`, `db.py:139` indexes `r["id"]`.

**Connection leaks: none found.** `src/db.py:62-63`'s `finally` always calls `putconn`. `_pool.getconn()` at `db.py:45` is outside the `try`, so a pool exhaustion raises `psycopg2.pool.PoolError` straight out of `get_connection` — I confirmed `PoolError` is a `psycopg2.Error` subclass, so it is *not* swallowed by the loop's handler (correct), but it also is not translated at the MCP boundary (see §5).

**Pooling is defeated by its own defaults — MEDIUM.** `DB_POOL_MIN` defaults to `1` (`src/db.py:37`). psycopg2's `_putconn` only returns a connection to the pool while `len(self._pool) < minconn`; every connection past the first is **closed** on release. Combined with the unconditional `SELECT 1` probe on every checkout (`db.py:46-48`), each concurrent call pays a fresh TCP connect plus an extra round trip. The docstring at `db.py:31-35` ("Check out a live connection from the pool") describes a 1-connection cache.

**Transaction discipline — fragile but correct.** Read paths never commit or rollback; correctness depends on psycopg2's `putconn` resetting the connection. `SET LOCAL hnsw.iterative_scan = relaxed_order` (`src/search.py:79`) silently relies on the implicit transaction psycopg2 opens — it becomes a no-op the moment anyone sets `autocommit=True`. LOW, worth an explicit transaction block or a comment.

**String-built SQL:**
- `src/db.py:155,159` — `set_clause` is f-string-interpolated into `UPDATE memories SET {set_clause}`. Not injectable, because keys are filtered through `ALLOWED_UPDATE_FIELDS` (`db.py:141-146`) and values are parameters. But the safety rests entirely on that allowlist with no identifier quoting. `src/search.py:22-27` already uses `psycopg2.sql.Identifier` correctly — `update_memory` should too.
- `src/db.py:188/194` and `db.py:261/266` join literal `"col = %s"` fragments; values parameterised. Safe.
- `src/search.py:76-134` uses `psycopg2.sql.SQL` / `Identifier` throughout. **This is the good pattern to standardise on.**
- `migrations/migrate.sh:21,29` interpolate `$VERSION` into SQL string literals. Input is a repo-controlled glob, so not attacker-controlled, but a filename containing an apostrophe breaks the runner. LOW.
- Out-of-scope but same class: `scripts/cleanup_duplicate_sources.py:114,119` (table name into DDL), `scripts/eval/recall_check.py:36-37`.

**No SQL injection vector found in the assigned modules.** Every caller-supplied value reaches Postgres as a bound parameter, including the `'; DROP TABLE memories; --` case that `tests/test_mcp_server.py:696` already covers.
