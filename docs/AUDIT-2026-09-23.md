## 0. The headline: 199 MB of captured content was never embedded

`src/ingest.py:63` `chunk_by_section(body, max_chunk_chars=4000)` does not enforce its own limit. It splits on `\n(?=##\s)`, falls back to `body.split("\n\n")`, then *merges* small pieces — but nothing ever **hard-splits** a piece that is already too big. Two inputs defeat it completely:

- a body with no blank lines (Slack joins its day with `"\n"` at `slack.py:141`; YouTube likewise at `youtube.py:138`) → `paragraphs` has one element → one chunk of the whole document;
- a single `##` section larger than the limit → emitted whole.

Measured on the live corpus:

```
body = 1,500 lines joined with "\n"  (74,289 chars)  → 1 chunk, 74,289 chars
body = "## H" + 50,000 chars                          → 1 chunk, 50,005 chars
```

`src/embeddings.py:24` then silently truncates: `generate_embedding(text, max_chars=25000)` does `text[:max_chars]` with no warning, no counter, and no log line.

| source_type | rows | rows > 25 k (embedding truncated) | rows > 4 k (declared chunk limit) | max chars |
|---|---|---|---|---|
| kiro_ide_chat | 73,250 | **4,240** | 17,713 | 262,662 |
| kiro_cli_chat | 3,405 | **291** | 1,148 | **1,283,484** |
| youtube | 1,527 | 167 | 1,053 | 242,536 |
| article | 3,081 | 64 | 951 | 265,882 |
| slack | 747 | 26 | 151 | 60,013 |
| codex_task | 117 | 6 | 65 | 76,218 |
| outlook_email | 203 | 0 | 13 | 20,013 |
| browser_history | 33 | 0 | 13 | 15,685 |
| outlook_calendar | 106 | 0 | 0 | 1,472 |

Corpus-wide:

```
rows over 25,000 chars        4,826
their total content            314 MB
never embedded                 199 MB   (63.4 % of the text in those rows)
rows over the declared 4 k      21,352
```

**S1.** Vector search cannot reach 199 MB of captured content. The largest single row — a 1.28 MB CLI chat — is represented by its first 2 %. This is invisible from every surface: the rows exist, `memory_search` returns them on keyword hits, and nothing reports a truncation. It also explains why retrieval can feel shallow on long sessions while the corpus count looks healthy. Full-text search is unaffected (`search_vector` is built from the whole column), so the failure is silent and partial, which is why it survived.

*Fix:* hard-split in `chunk_by_section`, add a property test (`max(len(c)) <= max_chunk_chars * 1.1` for header-less, blank-line-free input), make `generate_embedding` raise or count truncations instead of silently slicing, then re-chunk and re-embed the 4,826 rows. Re-embedding cost at Titan v2 v2 rates is small; the work is a batch job, not a redesign.

## 1. Routing and spend safety — stated rules are not enforced anywhere

Your standing rules are: corpus content never reaches Kiro or Fable 5.1; the dream cycle stays inside a $9 run cap. The skim role honours its rule beautifully — `us.amazon.nova-2-lite-v1:0` is pinned identically in all five profiles (`backends.toml:42,59,82,100,126`) and `assert_backend_supports_role` rejects any MCP-capable backend for it at config load, at resolver construction, at every resolution, and again defensively before the stage runs. That is the pattern. Nothing else has it.

**S1 — two paths spend on corpus content with no meter and no cap.**

- `src/express.py:481-483` — when no invoker is injected it constructs `AgentInvoker()`, which is `KiroInvoker` with a hardcoded `DEFAULT_MODEL = "claude-opus-4.8"` (`kiro.py:43`). The prompt is built from briefing items, i.e. corpus-derived titles and content. This bypasses the resolver entirely, ignores `SECOND_BRAIN_PROFILE`, takes no `SpendTracker`, and the `except Exception` at `:496` degrades to a deterministic fallback with one WARNING — so the violation is near-invisible.
- `src/capture/codex.py:189-212` — `_BackendSemanticPass.run` resolves `invoker_for("thinker")` and sends raw chat turns. Under `controlled` that is `bedrock/claude-opus-5` at $5/$25 per 1M; `result["usage"]` is discarded and no tracker exists. This runs every 6 hours via `com.second-brain.codex-capture.plist`. Unbounded metered spend on the most expensive configured model — and under `laptop`/`hybrid` the same call sends chat turns to Kiro, under `bedrock` to Fable 5.1.

**S2 — the default profile is the one the rules forbid.** `config/backends.toml:33` `default_profile = "laptop"` and `resolver.py:153` falls back to the same literal. `laptop` puts all six agent roles on Kiro. Every cron job overrides to `controlled`, so scheduled runs are safe; any manual invocation without `SECOND_BRAIN_PROFILE` is not.

**S2 — `hybrid` can route the corpus to Kiro *and* Fable simultaneously.** It puts explorer/thinker/advocate/methodologist on Kiro (`backends.toml:94-99`). `backends.toml:106-113` records that kiro-cli 2.22 ignores `--model` and server-side "Auto" served `claude-fable-5.1` — which Kiro labels not for PII. So `model = "claude-opus-5"` there is a request, not a fact, and `_note_model_honored` (`agentic_cli.py:228-243`) only logs a warning.

**S2 — no code enforces either rule, and a test pins one backwards.** `assert_backend_supports_role` (`base.py:169-206`) encodes exactly two rules, both about MCP. The prohibition exists only as two per-profile assertions in `tests/test_resolver.py:79-100`, while `tests/test_resolver.py:64` asserts `p["thinker"].model == "global.anthropic.claude-fable-5-1"` for the `bedrock` profile. A new profile, or `SECOND_BRAIN_PROFILE=laptop`, passes the suite.

**S2 — cost accounting has three gaps.**
- `SpendTracker.record` returns early when `cost == 0.0` *before* `self.calls += 1` (`cost.py:210-212`), so a metered call whose usage did not parse increments neither counter and logs nothing.
- Pricing and provenance both use the **requested** model (`orchestrator.py:190,219-225`), never the served one. A Sonnet-5 request served as Fable 5.1 bills $2/$10 instead of $10/$50 — a 5× understatement that cannot trip the cap.
- The cap is checked *after* each call, so one large Astra call can exceed it before anything notices. The skim sub-cap has the same shape at a harmless scale.

**S2 — the cap has four values.** `cost.py:39` $5 (library default), `backends.toml:71` "default 5.00", `backends.toml:119` "under the $6/run cap", `dream_cycle_scheduled.sh:33` **$9** (the effective value). `MODEL-BACKENDS.md:62` documents $5. No canonical doc states $9.

**S2 — a shipped job references a profile that does not exist.** `codex_capture_canary.sh:25` and `com.second-brain.codex-canary.plist` set `SECOND_BRAIN_PROFILE=codex_local`; `default_resolver()` raises `KeyError` for it. `codex_capture.sh:12` documents the problem and leaves it.

## 2. Failure visibility — green does not mean working

**S1 — the dream cycle reports zero work on every aborted run.** `orchestrator.py:498-506` promises "no zeroed-stats lie / orphaned accepted memories", and the evaluator-abort path honours it. The spend-cap path and the generic `except Exception` do not: both reach `run()`'s handlers at `:327-347`, which call `complete_run(run_id, stats=_ZERO_STATS, digest="")` — while accepted memories and candidate rows are already committed. Every tier-1 metric (acceptance rate, trend, cost efficiency) is computed from those columns and is therefore wrong for any capped run.

**S1 — one malformed LLM relationship discards a whole run.** `check_duplicate`, `store_accepted` and `store_candidate` sit **outside** the panel loop's `try` (which covers only the evaluator calls, `:522-531`). `storage.store_accepted:104-110` does unguarded `rel["target_id"]` / `rel["relation_type"]` on model output, so one bad key raises `KeyError`, unwinds to the generic handler, and zeroes the stats for every candidate already judged.

**S1 — nothing prevents two concurrent dream-cycle runs.** `run()` creates the run row unconditionally; there is no advisory lock or lockfile anywhere in the job surface. A launchd run overlapping a manual one gives two independent `SpendTracker`s — 2 × $9 — plus interleaved `record_slices`. `redistill_capped.py:208-221` has a lockfile for a far less expensive job. Separately, `backup.sh` (pg_dump) and the dream cycle both fire at 02:00 Mon/Wed/Fri against the same database with nothing serialising them.

**S2 — five channels exit 0 on failure.**
- `browser.py:291` missing Chrome History → `logger.error`, zeros, `main()` returns `None`, `capture_browser.sh` `exec`s it → exit 0 forever.
- `youtube.py:167` DB unreachable → same. And `youtube.py:184-190` increments `stats["processed"]` during `--dry-run`, so a dry run is indistinguishable from real work in the log.
- `ingest_staged.sh:46-50` logs `Crawlee ingest FAILED` then `exit 0` at `:70`, so its wrapper can never notify. (The `$?` it prints is already clobbered by the `if`.) The status file it writes has no crawlee field, so nightly failure looks identical to nothing-new.
- `scrape_bookmarks.py` never returns non-zero, including on its 1-hour Crawlee timeout.
- `qd_sync.sh` has no wrapper at all, so no notification; `set -e` means step 3 of 6 failing skips the rest and the summary line simply never prints.

**S2 — four scheduled jobs have no failure-notification path** (`ingest`, `qd-sync`, `codex-capture`, `capture-api`), and `capture-api` respawns forever on `KeepAlive=true` with its stderr log untouched since 2026-09-14.

**S2 — `weekly-digest` is red right now and nothing says so.** `launchctl list` shows `- 1 com.second-brain.weekly-digest`, from the Sep 21 600 s `KiroInvoker` timeout. The code was fixed in `e998f3b`, but no scheduled run has succeeded since and **nothing in the system reports "job X's last exit was non-zero N days ago."** Persistent red is visible only to someone who runs `launchctl list`.

**S2 — notifications are the only channel and cannot work headless.** `osascript -e 'display notification'` needs an active GUI session and Notification Center permission; both monitors append `|| true` so a failed notification is swallowed. On the Mac mini this delivers nothing and reports success doing so. Meanwhile `verify_liveness.sh:102-113` computes exactly the structured data a dashboard wants (label, age, threshold, severity) and throws the structure away into prose.

**S2 — the `/usr/local/bin` fix was applied to the two scripts that hurt, not to the shared wrapper.** `verify_credentials.sh:16-24` names `job_wrapper.sh` as a root cause of the nightly false alarm; the fix went into `verify_credentials.sh:42` and `verify_liveness.sh:25` only. `job_wrapper.sh:9` still exports just `/opt/homebrew/bin:$PATH`, so the other 15 job scripts can still reproduce the exit-127-misread-as-failure pattern. It also omits `postgresql@17`, which is why seven scripts each re-add it.

**S2 — broad `except Exception` hides programming errors in six stages.** `_allocate_attention:826` ("non-fatal; using Explorer slices as-is") will equally hide a `KeyError` in `enforce_budget`, after which the run proceeds unbudgeted and unledgered behind one WARNING. Same shape at `_load_skim_records:864`, `_skim_arrivals:954`, `invoke_explorer:737`, `digest.py:94`. One is fully silent: `digest.py:59-62` `except Exception: pass`, after which the digest asserts "No feedback was injected" — a false statement manufactured by a DB error.

**S2 — the highest-consequence swallowed exception is a confidentiality one.** `browser.py:99-103` `_import_bookmark_filters` catches broadly and falls back to `INTERNAL_DOMAINS = re.compile(r"\.amazon\.com")`. If that import ever breaks, internal `*.a2z.com` / `*.aws.dev` URLs are reclassified `public` and sent to Crawlee, silently.

**S2 — `except …: continue` converts systematic breakage into quiet skips.** `orchestrator.py:456` (Thinker per slice) and `skim/runner.py:207,245`, where a model failure and a *storage* failure both increment `result.failed` — so a completely broken `memory_skim` write path reports "N failed" and the run exits 0.

## 3. Retrieval and data-layer defects

**S1 — `memory_graph` is wrong for inbound edges.** `db.get_relationships` returns both directions (`WHERE r.source_id = %s OR r.target_id = %s`) and its JOIN already computes the correct neighbour: `ON m.id = CASE WHEN r.source_id = %s THEN r.target_id ELSE r.source_id END`. `mcp_server.py:404` then emits `r["target_id"]` unconditionally and discards the joined `m.title` / `m.type`. For an inbound edge the queried memory *is* the target, so the tool reports a self-link and drops the actual neighbour. A live inbound-only `extends` edge exists. Fix: alias the CASE expression the query already computes.

**S1 — 97 % of relationships are expired and `memory_graph` serves them anyway.** 22,461 of 23,216 `memory_relationships` rows have `expired_at` set. Only `express.py:242` filters `expired_at IS NULL`; `get_relationships` does not. Agents traversing the graph get overwhelmingly retired edges with no indication.

**S1 — the test suite reconfigures production.** `migrations/009_hnsw_recall.sql:27` is `ALTER DATABASE memory_bank SET hnsw.ef_search = 200;` with the database **named literally**, and `tests/conftest.py:84-101` applies every `migrations/[0-9]*.sql` unconditionally. Proof: `pg_db_role_setting` carries `ef_search=200` on `memory_bank` and `second_brain_codex_test` but **not** on `memory_bank_test`, although the rest of 009 ran there. Two consequences — the suite issues `ALTER DATABASE` against the live database, and recall tests run at the default `ef_search=40` while production runs at 200, so `test_rerank_drift.py` guards a different retrieval regime than it claims. Fix: `EXECUTE format('ALTER DATABASE %I SET …', current_database())`.

**S2 — 10 live rows are unreachable through the MCP surface.** `type = 'correction_episode'` exists in the corpus but not in `validation.MEMORY_TYPES` / `FILTERABLE_TYPES`, so `memory_search(type=...)` and `memory_list(type=...)` both reject it. Written by a non-MCP path — which is the general problem: there are **no SQL CHECK constraints or enums** (verified live), so `validation.py` is the only gate and every non-MCP writer (`ingest.py`, `capture/*`, `dream_cycle_db.py`, `scripts/migrate/*`) bypasses it by calling `db.create_memory` directly.

**S2 — an advertised search feature can never fire.** `type = 'schema'` has 0 rows, so the whole `schema_context` block (`mcp_server.py:193-208`) always returns `[]` while the `memory_search` docstring advertises it as live. `migrations/007` maintains a partial index for it.

**S2 — one MCP tool bypasses validation entirely.** `memory_recent_activity` (`mcp_server.py:360-378`) never imports `validation.py`; it hand-rolls clamps with different bounds (1–90 vs `clamp_days`' 0–365; 0–20 vs `clamp_limit`' 1–100) and `int("abc")` raises a bare Python `ValueError`, not the documented error shape. `validation.clamp_limit`/`clamp_days` already accept `lo`/`hi` overrides that **no caller uses** — which is precisely why this tool re-invented them. `memory_brief` has no `try/except ValidationError` at all. `memory_learn` runs one embedding + one `hybrid_search` **per topic** with no cap on topic count (its docstring says 2–4).

**S2 — error messages leak local infrastructure.** `_guarded` (`mcp_server.py:53-54`) forwards Postgres `e.diag.message_primary` verbatim, echoing the offending literal untruncated; and `OperationalError` / `PoolError` propagate by design, whose text embeds `connection to server at "localhost", port 5432`.

**S2 — 77,413 rows have zero readers.** The knowledge graph from migration 008 (`entities` 29,642, `entity_edges` 45,776, `memory_entities` 1,995) is written only by `scripts/migrate/migrate_quick_desktop.py` and read by nothing in `src/`. Plus ~16 MB of indexes at `idx_scan = 0` (`memories_metadata_idx` 13 MB, `idx_memories_encoding_context`, `idx_relationships_derived_from`, the `entities` set) maintained on the hot write path — while `memories.parent_id` has **no** index despite two hot predicates.

**S2 — the live FTS index name exists nowhere in the repo.** `migrations/001:36` creates an unnamed index (Postgres → `memories_search_vector_idx`, which is what `memory_bank_test` has); live `memory_bank` has `idx_memories_search_vector` (100 MB, 94 scans), a string that appears in no file. A rebuild from migrations produces a differently-named index.

**S2 — pooling is defeated by its own default.** `DB_POOL_MIN = 1` (`db.py:37`): psycopg2 returns a connection to the pool only while `len(pool) < minconn`, so every connection past the first is **closed** on release, and there is an unconditional `SELECT 1` probe per checkout. The docstring describes a pool; the behaviour is a one-connection cache.

**S2 — `ingest_content` commits parent and chunks separately** (`db.py:92-106`, one transaction per row). If chunk 3 of 9 fails, parent and chunks 1–2 are durable, the `source_url` is now in the table, and the next run **skips** it. The document stays permanently half-embedded with no marker. `capture/codex.py` is the only channel that gets this right — one transaction, `FOR UPDATE`, explicit `rollback()`.

## 4. The crawlee bug has relatives

The 6,163-duplicate incident was caused by `"" in text` used for identity. The same shape survives in five places:

- **`outlook.py:106-110`** — `received = (msg.get("receivedDateTime") or …or "")[:19]`, so a message with no timestamp yields `outlook://mail//<hash(subject|sender)>`. Every such message with the same subject and sender collapses onto one `source_url` and all but the first are dropped as "already captured". The hash has no body component, so two genuinely different mails in the same second from the same sender with the same subject collide by design. `event_source_url:152-154` is identical. **S1.**
- **`chat_extract.py:94`** — CLI conversation ids truncated to 12 chars for the staging filename, from which `batch_ingest_staged.py:67-69` derives `source_url`. A prefix collision means the second session is counted `skipped` and moved to `staging/ingested` — deleted-by-move, no error. The IDE side does not truncate, so the two halves of one channel have different identity strength. **S1.**
- **`scrape_bookmarks.py:21-30`** — `SKIP_PATTERNS` applies unanchored bare substrings (`login`, `signin`, `code.amazon`, `sim.amazon` with `.` unescaped) to whole URLs, and `browser.py:100` imports and applies it to all browser history. An article at `…/how-single-signin-works` is silently dropped from two channels.
- **`scrape_bookmarks.py:51-55`** — `load_indexed_urls` regexes URLs out of the **entire** `index.md`, not per row, so any URL appearing in a summary is treated as already-indexed and never scraped. This is the inverse of the crawlee bug: `crawlee.py` was fixed with a rigorous row parse and `build_source_map()`, while the bookmark side still reads the same file with the old loose regex. **These two readers of `index.md` must be unified.**
- **`browser.py:200-203`** — `canonical_url` drops any parameter whose name `startswith("ref")`, catching `refresh`, `reference`, `referrer`, `refinement`. Two distinct pages differing only in such a parameter collapse to one `source_url`.

Adjacent: `slack.py:243-249` compares a server-supplied `lastActivity` against a formatted timestamp **lexicographically**, so any format difference silently skips the DM for the whole window with no log line.

Two structural consequences worth calling out:

- **Timezones disagree by channel.** Slack and Browser use completed **local** days, Outlook a rolling **UTC** window, the chat parsers stamp UTC-from-epoch. The same afternoon lands under two different dates depending on who captured it. Worse, Slack and Browser both snapshot a **fixed-offset** tz (`datetime.now().astimezone().tzinfo`) and combine it with midnight, so on a DST-transition day one hour is attributed to the wrong day — and because both key dedup on the day URL, that hour is never re-read. `ide_chat.py:143` guesses ms-vs-seconds by magnitude and falls back to `datetime.now()` for a missing timestamp, dating an old chat as today.
- **`src/ingest.py:1` claims to be "the single path from content to PostgreSQL."** It is not: `capture_api._store_memory` and `capture/codex.py` both write `memories` via raw SQL. `capture_api` has no dedup and no chunking, so a repeat POST creates duplicates and its rows are structurally unlike the same document captured by a collector. It also writes `source_type` values `"browser_extension"` and `"email"` that exist in no taxonomy, and `"slack"`, which **collides** with the real Slack channel.

## 9. Tests

79 files / 27,327 lines against 64 source files / 17,513 lines — a 1.56× inversion, worst at `orchestrator.py` 1,201 → `test_dream_cycle.py` 2,723.

**S1 — isolation is order-dependent.** `conftest.py:104-135`'s `test_db` is **session-scoped and not autouse**, and it mutates the shared dict in place (`db.DB_CONFIG.update(...)`), redirecting all production code to `memory_bank_test` for the rest of the session. Four modules define a module-level fixture **also named `test_db`**, which shadows it and never touches `DB_CONFIG`: `test_ingest_doc_chunks.py:157`, `test_ingest_eventlog.py:157`, `test_ingest_interactions.py:122`, `test_enrich_qd_tags.py:225`. Each opens a raw `psycopg2.connect(dbname="memory_bank_test", autocommit=True)`, bypassing the pool. But the code under test resolves its own connection — `scripts/migrate/ingest_eventlog.py:204` `with get_connection()` — from the *un-overridden* `DB_CONFIG`.

Net effect: in a full alphabetical run, `test_capture_api.py` requests conftest's `test_db` first, so `DB_CONFIG` is already redirected and these four files are **accidentally** safe. Run any of them alone and `enrich_with_interactions(dry_run=False)`'s `UPDATE memories` lands on the live corpus. Their green status depends on an unrelated fixture in another file having run first.

*Attribution note:* live `memory_bank` has 1,803 `qd-feed://evt_%` rows, 323 carrying `interactions` metadata, while `memory_bank_test` has 0. That is equally consistent with a legitimate production `--enrich` run; I cannot attribute those 323 rows to tests and do not claim to.

*Fix:* make the `DB_CONFIG` override session-autouse, delete all four local fixtures, and rename the conftest fixture so shadowing is impossible.

**S2 — `conftest._apply_migrations` has three defects** beyond executing migration 009 against production (§3): it runs each file as a single `cur.execute` and swallows only `DuplicateTable`/`DuplicateObject`, so on a pre-existing test DB 001 aborts at its first `CREATE TABLE` and the remaining 7 indexes and the trigger are skipped; and it never writes `schema_migrations`, leaving the test database's ledger empty so nothing can determine what it has.

**Coverage gaps that matter:**

- **`chunk_by_section` has zero test references anywhere** — the function at the centre of §0.
- The corpus-routing prohibition is pinned only as two per-profile assertions, one of which asserts the violation (§1). No test asserts a global invariant.
- Neither unmetered spend path (`express.py`, `capture/codex.py`) has a test asserting it is metered or resolver-routed.
- `src/validation.py`, the sole vocabulary gate, is referenced by one test file.
- Exit-code contracts are tested for 4 surfaces; the three always-exit-0 offenders (browser, youtube, `ingest_staged.sh`) have none.
- The skim sub-cap is pinned in exactly one file.

**Good:** zero skips, zero xfails. `test_rerank.py` maintains a deliberate independent oracle (re-declared literals + `_oracle_overlap`) — exactly the right pattern, and `rerank_weights.py` is genuinely the single source of truth it claims to be. `test_mcp_server.py` covers `'; DROP TABLE memories; --`. Two blemishes on that record: `test_rerank.py:214-219`'s class docstring documents a formula that **omits** `context_overlap`, `superseded_penalty` and `staleness_penalty` — all three asserted 20 lines below in the same file — and `test_rerank_drift.py:29` imports two of the constants it is supposed to independently pin.

**Duplication:** `FakeStore` ×3, `FakeInvoker` ×3 (+`_FakeInvoker`), `FakeSession` ×2, plus `StubResolver`/`_FakeResolver`, `FakeClient`/`_FakeBedrockClient`/`FakeBedrock`, `FakeAdapter`, `Dummy` — the same three collaborators (resolver/invoker, skim store, Bedrock client) re-faked across ~11 files instead of living in `conftest.py`.
